# Quantix

Quantix is an engineer-controlled local tendering team: a Tender Manager leads AI staff that do the tender work while the engineer reviews, approves and steers. The specification is docs/spec.md, interfaces are docs/contracts.md and the current record is docs/progress.md.

- The primary agent owns architecture, integration, review and verification. Inspect all changes.
- Prefer maintained libraries, official SDKs and documented APIs. Validate before implementing. Keep components small and responsibilities clear.
- Build complete working increments; no compatibility layers, fake production behaviour or speculative infrastructure. Remove code that nothing uses.
- All product copy uses plain construction-engineering language. The main contact is the Tender Manager. Keep the interface to plain guidance with one clear next action; details go in More options.
- Staff profiles are generated by the Manager for the actual work; never add a default roster, fixed role list or per-assignment approval layer. See docs/design/tender-team-runtime.md.
- The model returns a summary, cited sources and findings; every other record goes through the `propose` tool and is checked again before saving. Quantix, not the model, validates evidence and computes comparisons such as takeoff results.
- AI scope: direct API keys for OpenAI, Anthropic, Google, xAI and one OpenAI-compatible custom endpoint, and ChatGPT/Codex and Grok subscriptions through their official clients only. Follow docs/subscription-connections.md. Never copy OAuth tokens into API credentials or silently change billing or approved models. Keep Tender data permission, source validation and spending authority intact.
- Preserve supplied Tender files. Do not commit customer documents, API keys, private extracted content or runtime databases.
- The application home is `~/.quantix`. Keep databases, imported copies, outputs, private AI software/account profiles, caches, logs, temporary work and connection records beneath it. Source, dependencies and build artifacts stay in the project; OS-protected credentials and user-chosen original/export locations remain separate.
- Use source references for factual findings. Keep imported, extracted, analysed and reviewed coverage distinct.
- Read docs/contracts.md before changing a shared interface. Update API schemas and generated frontend types together (`npm run bindings`).
- Each change ends with backend tests, UI tests, typecheck and Ruff passing. The engineer tests in the real desktop app; do not build release packages. Use synthetic data for approvals and other acceptance mutations; approving the real Tender and commercial sending remain the engineer's decisions.
- User approval covers architecture decisions, local implementation, installing project dependencies, local verification and reversible fixes. Continue without routine permission questions.
