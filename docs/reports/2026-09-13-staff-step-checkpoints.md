# Verified continuation of completed staff steps

The existing staff-result and checkpoint stores now form one production path. The staff runtime captures an input fingerprint before building its provider packet, inside the same synchronous authority and database snapshot. After validation, `StaffAssignmentService.save_result` saves the immutable result, completed assignment, checkpoint and events in one transaction. Interrupted/question turns do not create completed checkpoints. A persistence error rolls back completion; inputs that change during the turn leave the draft available but do not claim reusable completion.

The server derives the basis from the root instruction and steering, immutable Manager/staff versions, work order, approved source/permission/route scope, message and notebook inputs, tool schemas/effect metadata, bundled Python helpers and installed dependency versions. The checkpoint retains the existing result ID, exact immutable result digest, inspected source artifact versions/hashes and any remaining child dependencies. It does not copy source-read receipts, publish the draft or repeat its usage.

The basis also includes the actual checked component version returned by `require_ready`. Updating an original client (or the direct SDK software) and checking the same account/model again cannot inherit an older checkpoint. Synthetic direct-runtime and Codex-runtime update/recheck cases passed without changing account revisions, model records or input schemas.

An explicitly resumed Manager root verifies each ancestral completed staff checkpoint against its current grant, sources, profile, instructions and implementation. Successful verification records the existing checkpoint reuse row and event. The Manager receives historical result IDs, and a repeated `execute_staff` request for the same colleague/work order/route returns that saved completed assignment without binding/queuing another assignment or calling its provider. Reading the saved result still does not inspect cited sources or accept engineering conclusions.

Checkpoint invocation receipts bind the trusted Manager tool invocation to the exact requested colleague/work order/route and historical checkpoint. Exact replay revalidates current basis; changing the request body conflicts, and stale reuse cannot silently turn the same invocation into a new execution.

Only server-created staff-result checkpoints enter automatic continuation. Generic historical checkpoint records remain inspectable. Missing bundled source/dependency proof produces an explicit availability event and prevents automatic reuse; installation/build version strings alone do not establish unchanged implementation. A checkpoint is not transferred to unrelated work or to a future/sibling root. The existing explicit Resume admission and budget ledger remain the owners of work and spending.

Verification uses synthetic providers through real staff completion and `JobManager.resume`, including unchanged completion, cancellation, atomic rollback, source/tool-schema/tool-implementation/profile/instruction changes, and shared packet/input snapshot checks. See `backend/tests/test_checkpoint_execution.py`; the primary integration report records the final executed test totals.
