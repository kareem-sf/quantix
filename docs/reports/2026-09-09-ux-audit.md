# Quantix frontend and engineer workflow audit

9 September 2026. Read-only product and source review against `AGENTS.md`, `docs/spec.md`, `docs/contracts.md`, `docs/progress.md` and `docs/design/design.md`.

## Conclusion

Quantix has substantial engineering controls, source traceability and recovery information. Its main usability problem is that the engineer must also understand how the application is organised and how its AI connections work. The Manager surface exposes account configuration, team configuration, history and review forms before consistently identifying the next construction task.

Keep the existing visual direction and capabilities. Simplify the visible decision at each moment, show configuration when it is needed, and retain detailed evidence and controls in clearly named secondary views. A wholesale framework migration or a new visual theme is not warranted by this audit.

The first patch should concentrate on Settings, account setup and modal behavior. A later workflow increment should make the Manager the reliable starting point for importing, reviewing, pricing and producing documents.

## Evidence and limits

- **Code finding** means the cited source explicitly implements the behavior or lacks a control in the inspected component. It is not a claim that the behavior was exercised.
- **UX inference** means a likely consequence for a construction engineer unfamiliar with complex software. Its magnitude needs the engineer's acceptance session.
- The primary reviewer separately observed the running UI at 1440 × 960: the account dialog had a long scrollbar beside the Settings scrollbar, and mail settings, reusable notes and backups remained visible behind it. After an access check failed, the stepper visually returned to “1 Prepare” although account authentication and the selected model were available; the message broadly referred to account, model or work limits. These are observations supplied by the primary reviewer, not a browser session conducted by this report's author. No customer screenshots or names were copied into the repository.
- No tests, lint, typechecks, builds, provider requests or broad browser QA were run for this audit. Existing dirty files were preserved. This report is the only file written by this audit task.
- References are to the working tree inspected on 9 September, including uncommitted implementation. Line numbers can move in subsequent patches.
- The older no-tests language and delegation model in the beginning of `docs/progress.md` are historical; this review followed the current `AGENTS.md` override. Historical passes do not verify the current frontend.

## What already works well in the design and source

The navy navigation, white work surface, restrained teal accent and local fonts provide an appropriate foundation. The implementation has real empty states instead of seeded tender content. File originals remain accessible from the source drawer; earlier revisions are labelled. The Manager separates document-processing notes from AI findings. Quantity proposals, source confirmation, rates, supplier approval and local submission export remain distinct decisions. These distinctions should survive simplification.

Useful existing disclosure patterns include document reading notes, earlier plans, cell formulas, exact source identities and saved measurement details. The source viewer marks cited extracted text with a border as well as colour. The stylesheet includes visible focus rules and reduced-motion handling. The composer preserves an unsent instruction locally. AI setup distinguishes sign-in from a passed access check, explicitly names the selected model and shows where tender content will go.

Evidence: `src/features/Manager.tsx:56`, `:165`; `src/features/Sources.tsx:153`, `:184`, `:283`; `src/features/Estimate.tsx:179`; `src/features/Composer.tsx:19`; `src/features/TenderAI.tsx:31`, `:58`; `src/styles.css:47`, `:722`.

## Prioritised findings

### P1 — The Manager does not consistently own one next action

**Code finding.** `Manager` renders `TenderAI` and a separate Settings link before the empty/import state, conversation and document analysis (`src/features/Manager.tsx:95–118`). With no saved AI policy, the full simple-policy form opens automatically (`src/features/TenderAI.tsx:26`). With no account, it presents text directing the engineer to Settings plus a disabled approval button (`:52`, `:65`). Once documents exist but findings do not, the screen says to ask the Manager to review documents, without a concrete review action (`src/features/Manager.tsx:156–163`). The composer remains available independently of AI readiness (`:193–204`).

**UX inference.** The engineer must decide whether to add files, configure AI, write a prompt or approve settings. A novice can submit an instruction before prerequisites are complete and only then discover the blocker. This is contrary to the approved one-next-action principle.

**Recommendation.** Give the Manager a small state-based next-action area: Add tender documents; Finish AI setup; Review documents; Review proposed plan; Review the next decision; Open prepared documents. Show the relevant action and one sentence explaining it. Keep the flexible composer available as a secondary route. A configured account should be a compact status with Change, not a repeated configuration section.

### P1 — Settings and account setup accumulate several different jobs

**Code finding.** Settings renders AI connections, working preferences, the local data path, reusable notes, supplier mail and backups in one page (`src/features/Settings.tsx:30–100`). Supplier mail initially exposes server names, ports, security modes and credentials (`src/features/MailSettings.tsx:92–176`, followed by the incoming-mail fields). The global AI More options embeds an entire second connection-management interface (`src/features/AIConnections.tsx:8`). The account dialog includes status, action, model, Grok usage, account options and history; the advanced account options open further dialogs (`src/features/AISetup.tsx:163–178`, `:274–288`). The generic Settings CSS applies section padding and borders to every descendant section (`src/styles/features.css:353–365`).

**UX inference, supported by the primary reviewer's visual observation.** A narrowly scoped goal such as connecting Grok becomes a long page of related and unrelated choices. Nested panels and nested disclosures increase the effort needed to recover one's place. More options is useful only if its contents remain structured and exceptional.

**Recommendation.** Keep AI accounts visible in Settings; use compact summaries for Working preferences, Supplier mail, Reusable notes, Local files and Backups. Open one focused section when requested. Keep account setup's primary state, selected model and actual next action together. Put software identity, exact models, billing detail and history behind one clearly structured More options area. Do not conceal the active error, its remedy, a charge approval or a tender-data permission.

### P1 — A failed check is presented as a return to preparation

**Code finding and primary-reviewer observation.** `SetupSteps` maps only ready/check/model/discovery and credential/sign-in states explicitly; `attention` falls back to index 0, Prepare (`src/features/AISetup.tsx:183–186`). The primary reviewer observed this after an actual failed access check while authentication and a selected model remained available. The attention state's next-action copy is generic, and its Try again button dispatches refresh (`:67`, `:171`).

**Impact.** The visual progress indicator contradicts the completed setup history. It can lead the engineer to repeat preparation or sign-in even though the failure occurred later. A broad account/model/work-limit message does not identify what needs changing.

**Recommendation.** Preserve the last completed steps and mark the failed check at Check. Show the specific known blocker and a relevant recovery action; retain uncertainty when diagnostics do not establish the cause. Do not imply that authentication or installed software has been lost merely because the model check failed. Include this correction in the minimal setup patch if the existing account/check fields establish the failed stage reliably.

### P1 — The shared dialog's focus handling is incompatible with closed disclosures

**Code finding.** Initial focus selects the first input/textarea/select whether it is visible or inside a closed `details`. The trap likewise enumerates hidden controls, omits `summary`, and does not make background content inert (`src/components/ui.tsx:65–102`). It has no fallback focus target when an asynchronously loaded panel lacks a usable input. Grok's closed spending disclosure retains radio inputs in the DOM (`src/features/AISetup.tsx:208–217`), providing a concrete affected composition. Close and Escape are handled centrally (`src/components/ui.tsx:77–79`, `:114`).

**UX inference.** Focus can remain outside the dialog or fail to wrap through the actual visible controls. On a long form, automatically focusing an input lower down can also bypass the status and explanation. A modal declared with `aria-modal` should behave as modal for keyboard users.

**Recommendation.** Fix the shared primitive before adding further disclosures. Use a documented dialog/focus implementation or correctly account for visible tabbable controls, `summary`, nested dialogs, async content, background inertness, initial heading focus and return focus. Preserve Escape/close semantics and keep a visible exit. Follow the [WAI modal dialog pattern](https://www.w3.org/WAI/ARIA/apg/patterns/dialog-modal/). Actual keyboard behavior remains to be checked in the authorised acceptance session.

### P1 — A sent instruction remains an editable, sendable draft

**Code finding.** After a successful send the composer marks `sent` and clears persistent storage, but leaves `draft` unchanged (`src/features/Composer.tsx:31–33`). It tells the user the copy stays while the Manager works (`:44–47`). Enter sends and the button becomes enabled whenever the Manager is no longer busy; neither guard checks `sent` (`:25–26`, `:70–79`, `:94`). The textarea remains editable during the awaited send, so the successful completion can clear storage for newer text typed during that request (`:31–33`, `:60–68`).

**UX inference.** The engineer can repeat work or incur another model request by pressing Enter after completion. A newly edited instruction can appear on screen while its persisted draft has been removed.

**Recommendation.** Separate submitted text from the current draft. Clear only the exact draft that was submitted after durable acceptance; preserve any newer edits. Keep failed submissions editable. If resending is supported, make that an explicit action on the sent message.

### P1 — Opening drawing measurement loses the current page

**Code finding.** `SourceDrawer` knows `activePage`, but passes only tender and artifact IDs to `Measurements` (`src/features/Sources.tsx:105`, `:132–136`). `MeasurementPanel` starts at page 1 (`src/features/Measurements.tsx:53`).

**UX inference.** An engineer inspecting a cited drawing page and selecting Measure drawing is moved to a different page. This causes avoidable navigation and risks measuring the wrong drawing before noticing the changed page.

**Recommendation.** Pass the exact current artifact version and page into measurement, show them clearly, and preserve that page on return. This is a bounded frontend interface change; inspect all callers and preserve the source identity rules.

### P2 — Source inspection is too difficult for large tender documents

**Code finding.** The PDF toolbar offers Previous and Next with no page entry or total; Next has no upper bound (`src/features/Sources.tsx:203–219`). The image is fit to drawer width without viewer zoom controls (`:223–229`; `src/styles/features.css:553–558`). Workbook inspection is a sequence of 30 extracted passages, with cell values/formulas inside each passage, rather than a sheet/range navigator (`src/features/Sources.tsx:93–99`, `:235–264`, `:281–314`). Measurement has a page total and bounds, demonstrating an existing source of PDF page metadata (`src/features/Measurements.tsx:119–127`).

**UX inference.** Engineers cannot efficiently go to a drawing or verify detailed dimensions in a large sheet. On the reference package's long specification, repeated Next is particularly costly. A source chip can open one passage efficiently, but general file inspection is much less usable.

**Recommendation.** Add bounded page entry, total pages, Fit width and readable zoom, preserving the cited location. For workbooks, offer sheet selection and jump to a cell/range before the raw extraction view. Keep formulas and original download accessible. Make unsupported preview guidance name the useful alternative.

### P2 — Documents and submission requirements are hidden under Estimate

**Code finding.** Estimate appends rate proposals and then `Outputs` after the BOQ table and pagination (`src/features/Estimate.tsx:246–251`). Outputs contains all draft document types, the submission-requirement register and reviewed local exports (`src/features/Outputs.tsx:42–84`, `:124–125`). Work combines plans, task results, every run, supplier requests and AI usage (`src/features/Work.tsx:220–273`).

**UX inference.** An engineer seeking the construction programme, technical document or final package must know that these live below pricing. A supplier reply is below run history. Navigation reflects implementation modules more than engineering tasks.

**Recommendation.** In a later workflow increment, give prepared documents and requirements a clear named destination, and make supplier requests reachable from the Manager's current action. Retain Work as the task/result view; put detailed run and AI usage history in More options. Do not solve this by exposing every feature as a top-level tab.

### P2 — Current work competes with the entire conversation and record

**Code finding.** The Manager renders every message, then all findings and the current plan (`src/features/Manager.tsx:120–191`). There is no explicit new-message indicator, jump-to-latest control or scroll positioning logic in this component. Work renders all run rows (`src/features/Work.tsx:245–252`). Context shows the first four current files and first five questions without a count or link to the remainder (`src/features/Manager.tsx:352–374`).

**UX inference.** The action the engineer needs becomes farther away as the tender develops, and a new response may be easy to miss when reading older material. Browser scroll anchoring and the severity of this problem have not been exercised.

**Recommendation.** Keep the current decision and work state easy to reach. Collapse older conversation and completed history, provide a new-response affordance when the engineer is reading elsewhere, and label partial context lists with a total and View all action. Preserve full history for inspection.

### P2 — Draft preservation is inconsistent across navigation

**Code finding.** Manager is retained with React Activity, while Files, Project map, Work and Estimate are conditionally mounted (`src/App.tsx:252–304`). Settings is also conditionally mounted (`:146–148`). The quote editor and programme/client-copy form store unsaved data only in component state (`src/features/Quotes.tsx:159–167`; `src/features/OutputForm.tsx:35–42`). Only the composer uses the local draft helper. Closing a modal invokes its caller's close function without a general draft policy (`src/components/ui.tsx:77–79`, `:114`).

**UX inference.** Closing a substantial form or leaving a tab can discard work, while other parts of the app preserve it. That inconsistency makes users reluctant to inspect a source or leave a form to fix a prerequisite.

**Recommendation.** Preserve ordinary non-secret drafts by tender and task, including selected source IDs and revision basis. Resume them with a clear draft label; invalidate approvals when relevant content changes. Avoid a confirmation dialog on every navigation. Secrets need a deliberately separate storage policy. Do not infer that all forms can safely be autosaved as approved records.

### P2 — Errors retain messages but lose the field and recovery structure

**Code finding.** API validation errors are flattened to a deduplicated list of `msg` strings; field locations are discarded (`src/api.ts:41–63`). `ErrorNotice` renders raw error text in a generic alert with no field links or recovery action (`src/components/ui.tsx:5–10`). Generic account attention maps to Try again that dispatches refresh (`src/features/AISetup.tsx:67`, `:171`); the renderer does not distinguish sign-in repair, model access, unavailable software or billing recovery in that state. Many features return only an error notice if initial data cannot be read, for example Settings and Estimate (`src/features/Settings.tsx:11–12`; `src/features/Estimate.tsx:38–39`).

**UX inference.** An engineer can see an accurate backend error yet still not know which field to fix or whether retrying will help. Long raw diagnostics also compete with the account's simple action.

**Recommendation.** Preserve structured field errors and render them next to the relevant answer, with a focused summary where helpful. Give recoverable failures one explicit action. Keep the short cause, effect and remedy visible; keep technical diagnostics in details. The [GOV.UK error-summary guidance](https://design-system.service.gov.uk/components/error-summary/) is a useful pattern for linked field errors and focus, not a requirement to copy its entire visual system. The retry concern here is a UI mapping finding; the backend refresh behavior was not exercised.

### P2 — Typography and important targets are smaller than the agreed design

**Code finding.** The design specifies 16px body, 15px captions/source chips and 14px small status, with at least 36px controls in small windows. Current source chips and finding actions use 12px; finding actions have 27px minimum height, and run controls 25px (`src/styles/features.css:90–107`, `:422–424`). Manager prose is 14px, plan descriptions 13px, source text 13px (`:153–157`, `:184–186`, `:574–580`). Small-window status text drops to 10px and composer help to 11px (`:624–626`, `:645–652`). Global status is 12px (`src/styles.css:274–281`).

**UX inference.** Critical evidence, status and recovery controls are the elements that become smallest. This works against quick reading and reliable pointer use on ordinary site laptops.

**Recommendation.** Restore the agreed type scale and at least 36px targets for ordinary actions; use 40–44px for frequent primary actions where appropriate. Reduce visible content before reducing font size. Do not call every current small control a WCAG failure: the [WCAG 2.2 target-size guidance](https://www.w3.org/WAI/WCAG22/Understanding/target-size-minimum.html) has spacing and other exceptions, and rendered geometry was not measured here.

### P2 — Routine actions require repeated free-text attestations

**Code finding.** Every `DecisionForm` requires a blank Decision note, including plan approval and finding acceptance (`src/features/Work.tsx:118–159`; `src/features/Manager.tsx:288–299`). Creating a routine draft requires both a review note and a checkbox (`src/features/OutputForm.tsx:113–130`). Linking a generated document to a requirement also requires a rationale and checkbox (`src/features/SubmissionRequirements.tsx:180–183`). Stronger commercial and final-export approvals are separately implemented and necessary.

**UX inference.** Repeated empty note fields invite boilerplate and slow review without necessarily improving engineering judgment. The same confirmation pattern makes a routine draft look as consequential as a changed quantity or outgoing supplier message.

**Recommendation.** Preserve deliberate approval of exact consequential scope. For routine actions, consider recording the explicit clicked action and displayed scope as the audit description, with a note optional unless the action is an exception. This requires a deliberate contract/backend review where rationale is mandatory; hiding or fabricating an approval is unacceptable. Keep material assumptions, pricing/quantity changes, external sends and final export explicit.

### P2 — Recording a source review is separated from inspecting the source

**Code finding.** Record source review begins from Project map (`src/features/ProjectMap.tsx:41`), then asks the engineer to choose the file again, choose a scope and locate the passage (`:182–202`, `:205–212`). The source drawer does not offer a current-page/current-passage review action. A related BOQ record tells the user to open Estimate rather than offering a direct handoff (`:176`).

**UX inference.** Users must remember the source location and repeat selections, or skip recording their review. The implementation's good distinction between read and reviewed becomes expensive to maintain.

**Recommendation.** Offer Record my review next to an inspected page/passage, preselecting only the exact visible scope. Keep whole-document review a separate explicit action. Add context-preserving Open in Estimate/Work links instead of navigation instructions.

| Record source coverage | Inspect source → close → Project map → Record source review → reselect file/scope | Record review of this page/passage |

These are source-derived paths, not measured usability task results. Keep the Tender Manager flexible; the recommendation is guidance based on current state, not a rigid wizard for the whole tender.

## Progressive disclosure rules for Quantix

The primary view should answer: What has happened? What requires my engineering judgment? What should I do next? Use short construction language, an actual current status, and one prominent action. Put original-source access next to the finding or decision it supports.

| Visible by default | In More options or a focused secondary view |
| --- | --- |
| Current setup failure and precise recovery action | Software versions, account IDs, exact model capabilities, check history |
| Selected account/model and required tender-data permission | Role routes, saved alternatives, token/request limits |
| Expected charge or relevant spending restriction at approval | Token accounting, provider-versus-estimated usage detail |
| Current task, result and decision | Completed runs, event logs, technical fingerprints |
| Source location, current revision, missing coverage and relevant warning | Hashes, duplicate relationships and low-level extraction detail |
| Quantity/rate/tax basis required for the decision | Previous proposals, full calculation history and secondary provenance detail |
| Files included in export, scope and material gaps | Manifest identity and archived review history |

Do not hide information required to decide or recover merely to make a screenshot shorter. The [GOV.UK details guidance](https://design-system.service.gov.uk/components/details/) supports disclosure for information needed by only some users and cautions against hiding information most users need.

Recommended plain-language replacements include Account rather than connection profile, Where tender documents are sent rather than data destination, Work history rather than run history in the normal flow, Money held for unfinished work rather than reserved usage, and Why this needs attention rather than raw status codes. Keep precise engineering terms such as BOQ, quantity, rate, tax basis, source revision and reviewed scope.

## Frontend architecture and dependencies

The current React, TanStack Query, Tauri, locally bundled Inter and Lucide stack is suitable. Generated API types are a useful shared contract. This audit did not perform a package-security assessment or establish a need to upgrade/change libraries.

Several structural changes would make future simplification safer:

1. **Separate state decisions from page composition.** Account stage labels/actions, Tender policy readiness, team warnings and Manager work state are currently computed in different components. A shared presentation-level readiness result should identify the blocking reason, action and destination while leaving execution authority in the backend. This prevents repeated configuration and contradictory action labels. Start with existing API fields; add shared fields only through `docs/contracts.md` and regenerated bindings.
2. **Separate forms by responsibility.** `AISetup.tsx` contains service selection, account operations, sign-in, key entry, model choice, subscription settings and check history. It is about 38 KB; some JSX lines exceed 2,700 characters. `TenderAI.tsx` and `AIAdvancedConnections.tsx` each exceed 30 KB. `Quotes.tsx` is 1,093 lines and `Measurements.tsx` 759. These are maintainability measurements from source, not runtime performance results. Extract bounded state hooks and focused views, retaining the same contract and avoiding a large rewrite.
3. **Narrow invalidation and polling.** `useRefresh()` invalidates every query (`src/api.ts:98–100`). General polling occurs every two seconds (`:89–96`), including Manager messages/runs and Work history. Account setup additionally polls every 1.5 seconds and invalidates the account list as results change (`src/features/AISetup.tsx:124–139`). Use mutation-specific query keys and active-work polling. TanStack Query documents [targeted invalidation](https://tanstack.com/query/latest/docs/framework/react/guides/query-invalidation). No polling-load or responsiveness measurements were made.
4. **Avoid accidental eager feature loading.** App statically imports every major view; Files imports DocumentSearch, which imports Work just for RunRow, bringing in quotation and AI UI dependencies (`src/App.tsx:12–19`; `src/features/DocumentSearch.tsx:6`; `src/features/Work.tsx:14–16`). Move small shared run/decision primitives out of the full Work feature. Consider [React lazy loading](https://react.dev/reference/react/lazy) for large optional editors when profiling supports it. Do not invent bundle-size or startup-time claims without a build/profile.
5. **Make long-lived state and recovery explicit.** Add a common non-secret draft policy, a consistent form-error shape and a reliable shared dialog. Consider a feature error boundary with recoverable local navigation; no frontend error boundary was found in the inspected source. These foundations are more valuable than adding more isolated visual components.

## Minimal first patch

This patch can improve the observed Settings experience without redesigning every journey or changing backend approval policy.

1. Keep AI accounts as the normal Settings content. Present preferences, reusable notes, mail and backup/local-file controls as concise named disclosures or focused sections. Preserve every existing capability and status.
2. Keep the account dialog's status, short issue, model and next action visible together. Make technical/software/history detail secondary; avoid repeating the same status and guidance in multiple panels. Show More options once at the account level with clear internal headings.
3. Repair modal initial focus and traversal for closed disclosures and nested panels. Keep the status/title visible on opening instead of automatically jumping to an input deep in a long form.
4. Remove broad descendant section styling from Settings in favour of intentional top-level section classes, so nested account content is not repeatedly padded and bordered.
5. Preserve actionable errors and any charge/data approval in the default view. Copy changes must remain accurate for all stages, including a paused account, sign-in still running, a failed model check and uncertain earlier charges.

Keep this patch separate from the composer send-state fix and drawing-page handoff fix; those are small, important reliability follow-ups with distinct behavior. The wider Manager next-action design and document navigation can follow as a complete working increment.

## Later redesign sequence

First establish a common state/action pattern and preserve drafts. Then simplify the Manager and its latest work/decision view. Next improve source inspection and in-context engineering review. Finally reorganise documents/requirements and supplier work around their actual engineering tasks. Preserve advanced capability behind deliberate entry points throughout.

The engineer's later acceptance should cover first use, a configured account, a failed access check, ordinary import, a changed source, a long conversation, a quotation draft, a BOQ review, a drawing-page measurement, a local export and restart recovery. It should also cover keyboard traversal and a small laptop window. These are proposed acceptance scenarios only; none were executed by this audit.
