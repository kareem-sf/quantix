# AI connection and runtime audit — 9 September 2026

## Conclusion and scope

The current Grok check failure is explained by a permission mismatch: Quantix's bare `Read` denial also blocks Grok's required local tool discovery. The primary agent observed three denied `search_tool` attempts in the latest generic-check session; the upstream permission implementation explains those denials. A separate three-round check budget is also too short for the ordinary discovery/check/submit/final-response sequence.

Keep the existing separation between the Quantix core, managed provider workers, and original subscription clients. Fix the permission scope, protocol-specific check limits, incomplete diagnostics and setup errors that lose their actionable cause. These findings do not justify switching the engineer's account, model, billing route, or provider.

This is a read-only source and official-documentation audit. No account, credential store, customer file, runtime database, process, or live AI request was inspected or changed by this auditor. No tests, lint, typechecks, browser QA, or builds were run. The primary agent's separately conducted live check is explicitly attributed below; this auditor did not reproduce it. Source line numbers describe the files at audit time; concurrent implementation can move them.

### Source proof for denied discovery

The primary agent inspected only structural fields from the provider-owned latest generic-check session: three loop starts, each with `search_tool`, a permission request and `decision=deny`, followed by cancelled completion. The check tool and submit tool were never reached. These observations establish the current failure before any structured exchange, rather than a bad account or selected-model result.

Pinned upstream `AccessKind::from` does not give SearchTool a file path; it falls through to `Read(None)`. The dynamic fallback likewise returns `Read(None)` for a search query. In contrast, `UseTool` is classified as `MCPTool` with the inner qualified target name, so Quantix's current `MCPTool(quantix__*)` rule is already appropriate for actual dispatch. [Access-kind source](https://github.com/xai-org/grok-build/blob/72a61251/crates/codegen/xai-grok-workspace/src/permission/types.rs#L246).

The policy matcher treats an absent pattern or `*` as unrestricted. For any other pattern, `Read(None)` returns false; real read paths go through path matching. Therefore `Read(**)` blocks file paths while avoiding this no-path discovery collision. The permission manager allows read access by default when no overriding rule forces a prompt. Keep the CLI/profile tool allowlists in place, so this adjustment does not expose other read-capable tools. [Rule matching](https://github.com/xai-org/grok-build/blob/72a61251/crates/codegen/xai-grok-workspace/src/permission/policy.rs#L738), [read-only decision](https://github.com/xai-org/grok-build/blob/72a61251/crates/codegen/xai-grok-workspace/src/permission/manager/mod.rs#L2128).

The same upstream file documents leading `**` as an unrooted pattern matching any depth (`779–781`). It checks normalized absolute paths plus valid working-directory-relative forms (`782–811`) and normalizes Windows backslashes to `/` (`875–876`). This supports the intended absolute/relative and Windows/POSIX path coverage by source inspection. No cross-platform execution or filesystem-sandbox guarantee is claimed.

Adding `MCPTool(search_tool)` would target the wrong access class. Adding an allow while retaining the broad read denial would still lose to deny precedence. `use_tool` does not need an unrestricted meta-tool grant: its permission check uses the inner Quantix-qualified name. This is source-backed correction advice; the adjusted configuration still requires the targeted joint check.

### Source proof for the secondary Grok check round limit

The primary agent reports that its separate native check ended at Quantix's `grok.py:249` failed-marker message. That message merges native `error` and `max_turns_reached`, so it does not alone identify which event occurred.

Pinned upstream `turn.rs:2369` initializes `tool_turn_count` to 1. It executes the current tool batch at line 3409, then calculates the next round and returns `MaxTurnsReached` if it would exceed the configured limit (`3439–3449`). The headless projector distinguishes that outcome through cancellation metadata, emits the max-turn marker followed by final accounting, and returns an error (`headless.rs:1302–1311`). This is a real terminal failure, even when a tool in the last allowed round completed. [Turn-loop source](https://github.com/xai-org/grok-build/blob/72a61251/crates/codegen/xai-grok-shell/src/session/acp_session_impl/turn.rs#L3439), [headless source](https://github.com/xai-org/grok-build/blob/72a61251/crates/codegen/xai-grok-pager/src/headless.rs#L1302).

Grok's MCP discovery returns tool schemas, and `use_tool` expects a previously discovered qualified tool name and arguments built from that schema. Quantix exposes only those meta-tools to Grok and does not put the check/submit schemas into its instruction. [Discovery source](https://github.com/xai-org/grok-build/blob/72a61251/crates/codegen/xai-grok-tools/src/implementations/search_tool/mod.rs#L224), [dispatch source](https://github.com/xai-org/grok-build/blob/72a61251/crates/codegen/xai-grok-tools/src/implementations/use_tool/mod.rs#L15).

The normal minimum sequence is therefore: round 1 discovers both tools; round 2 calls the check tool to obtain the unpredictable value; round 3 submits that value; round 4 completes the original-client turn. A three-round cap stops after submission. Searching for the tools in separate rounds needs another round. This establishes an adapter/check-budget mismatch; the exact live event sequence still needs sanitized observation. A narrowly derived Grok-specific allowance and explicit discover-both instruction can fix that mismatch without changing ordinary Tender limits. The allowance must be represented in `ai_setup.py:318`, `ai_worker_client.py:367`, worker `server.py:105` and the check meter rather than changed only in the native command.

## Architecture choices to retain

- The core owns Tender permissions, budgets, source provenance, review authority, and atomic publication. Provider workers receive a scoped source bridge and a separate private control bridge (`ai_worker_client.py:325–357`).
- Grok uses its original OAuth client and a private account home. It rejects API-key credentials for the subscription route (`grok.py:138`) and rechecks account allowance while holding an account lock (`grok.py:162–174`). Account changes and software changes invalidate readiness proof (`ai_readiness.py:23–33`).
- Subscription-only behavior stays fail-closed. Optional provider-managed extras do not imply a locally enforced dollar cap. API-key Grok remains a separate explicitly chosen connection.
- Grok runs with native tools/subagents restricted, local MCP authorization, a bounded stream and explicit final-result validation. The current configuration uses documented per-model completion/retry fields; its scope restrictions are appropriate but should not be described as an OS filesystem sandbox. [Pinned configuration reference](https://raw.githubusercontent.com/xai-org/grok-build/72a61251/crates/codegen/xai-grok-pager/docs/user-guide/26-config-reference.md).
- Managed installations use publisher integrity data, platform locks, immutable receipts and leases. Repair preserves private account state (`ai_components.py:294–422`). A valid receipt proves installation consistency, not successful provider access.

## Provider support truthfulness

The manifest currently declares API components for OpenAI-compatible, Anthropic, Google, Bedrock, Mistral and Cohere adapters; original-client components cover Codex, Claude Agent, Copilot, Gemini CLI and Grok Build. API loops use Pydantic AI and provider SDKs (`provider_factory.py`, `execution.py`). That is a sensible way to avoid implementing provider HTTP protocols independently. It remains an implementation inventory rather than a verified support matrix.

The original-client families match documented integration directions: the OpenAI Python SDK controls local app-server with its pinned runtime, Copilot documents a matching bundled/downloaded runtime managed by its SDK, Gemini documents ACP authentication and session operations, and Claude provides its Agent SDK. [OpenAI SDK](https://learn.chatgpt.com/docs/codex-sdk), [Copilot runtime](https://docs.github.com/en/copilot/how-tos/copilot-sdk/setup/bundled-cli), [Gemini ACP](https://geminicli.com/docs/cli/acp-mode/), [Claude Agent SDK](https://code.claude.com/docs/en/agent-sdk/overview).

Retain separate labels for available adapter, installed software, signed-in account, discovered model, passed model check, and accepted Tender execution. Do not promise that every compatible endpoint supports the same tools, structured output, images, reasoning controls, pricing, or web search. The current [support table](../ai-provider-support.md) mostly makes these boundaries explicit. Its title should remain dated and its opening limitation should remain visible.

Documentation currently conflicts in places: the early AI-worker contract in `docs/contracts.md:53` still describes a single official Agents SDK route while the later universal integration contract and current code use Pydantic AI/worker adapters. `docs/grok-subscription.md` still says no live checks or tests were performed, while the later repair report records targeted joint acceptance. Reconcile those descriptions without turning historic narrow results into broad verification.
