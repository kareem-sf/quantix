# Shared implementation contracts

## Package analysis and Tender authority — 13 September 2026

Creating a Tender grants no AI destination, route, paid allowance or provider-managed extras. The engineer selects and confirms AI for that Tender through its existing AI setup. Import can complete local analysis while AI mapping waits for this decision.

Automatic identity results are proposals, retained in the run result/package map and labelled for source review. They can supply a provisional AI name but cannot update engineer-maintained Tender profile fields or create engineer decisions. Package-map tools return no whole-Tender context to a scoped specialist; scoped source readers remain available.

Document brief cache version 2 binds reuse to the Tender, full current artifact metadata, document IDs/paths and every opening excerpt supplied to the model. Relationships must name another document in that model batch. Identical file bytes in another Tender or changed extraction context require a fresh brief. Older content-only cache entries remain stored but are not reused.

## Audit repairs — 13 September 2026

`SourceBoqProposal.replaces_item_id` is optional for a new row and names the exact earlier source-BOQ row when proposing its replacement. It is preserved in the immutable proposal basis and is never inferred from a repeated row label.

`EstimateView.retired_source_rows` keeps earlier source-BOQ rows visible after revisions. They block complete totals until a source proposal explicitly naming `replaces_item_id` is confirmed, or the engineer records that the old row is no longer required. Replacements must use a newer revision of the same source file and identify the exact old row, so repeated row labels on separate pages cannot collapse. Confirmed replacement chains transfer pending scope to their latest unresolved row. `POST /tenders/{tid}/estimate/source-rows/{id}/exclude` takes `SourceRowExclusion {engineer_confirmed:true,rationale,current_artifact_id}`; the last field must match the revision displayed during review. The immutable `boq_source_exclusions` basis joins the immutable decision ledger, so a later file revision requires renewed review. Old originals and BOQ records remain preserved.

Source BOQ proposals use `POST /api/tenders/{tid}/estimate/source-rows` with `SourceBoqProposal {source_id,row_reference,source_excerpt,description,unit,quantity}`. An exact current preserved passage must contain the supplied excerpt, quantity and unit. The operation creates an **unconfirmed** `EstimateItem`; existing explicit source, quantity, price, tax and release decisions remain authoritative. `OfficeOutput.boq_item_proposals` permits the Manager to publish the same unconfirmed rows using inspected evidence; staff require the explicitly reviewed output kind. Saved identity is source ID plus row reference, so one page may support multiple rows; altered retries conflict. Source proposals remain separate from calculated quantity proposals. `EstimateItem` adds optional original proposal/excerpt/reference/origin/run fields. Normal refresh retains current source proposals and retires rows whose original source revision is superseded.

Database schema version 2 replaces the obsolete unique `(tender_id,source_id)` BOQ key with `(tender_id,source_id,row_key)`; Excel rows retain an empty key and every prior item ID and foreign-key relationship survives. The versioned startup migration snapshots the database, commits atomically after foreign-key validation and restores on failure. Backup schema 1 and 2 are readable; a new manifest records the actual database schema and inspection verifies it. A checked pre-change backup precedes activation on the real idle workspace.

`RequirementProposal` adds `source_quote`, `applicability` (`unconditional|conditional|unknown`), `condition`, and `exceptions`. New Manager proposals must quote an actual inspected clause and explicitly preserve known conditions/exceptions. The lexical guard includes the enclosing source line to catch omitted prefixes; it is not a guarantee of complete semantic interpretation. Old payloads remain immutable and project unknown applicability with review warnings. `RequirementDecision.applicability_reviewed` is explicit non-autosaved engineer acknowledgement for unknown/conditional/exception-qualified requirements. Its receipt is retained in the decision ledger; unreviewed qualification blocks final package review. Source text, applicability and exceptions remain visible in the UI.

`ResultLink.kind` adds `requirement`, `boq_item`, `work_product`, and `calculation`. Links join exact owning-run records/events to existing same-Tender records; IDs in generated prose do not establish links. Requirement and BOQ links select their existing Submission/Estimate records; work-product and calculation links open addressed Manager workspaces with source/history inspection.

`WorkBrief.progress_current` and `latest_work_run_id` are derived read-only projections. Later completed material engineering work makes an older brief explicitly out of date without rewriting its steps or inventing completion. Material Manager continuation requires a newly saved brief before publication; greetings and plain specialist assignments do not rewrite Manager progress. A missing update is an actionable correctable model error. The interface does not present an old next step as current and links saved drafts directly.

Analysis DOCX captures the latest Manager message belonging to a completed engineering outcome (including conversation runs that entered engineering). Ordinary conversation and failed/unknown outcomes do not replace the analysis. No attributable analysis yields an explicit note; source changes still invalidate the draft, while unrelated greetings do not.

## Dynamic Tender Office implementation (10 September 2026)

The accepted [live office design](design/live-dynamic-office.md) extends the current workspace. The interfaces in this section are implementation contracts; the execution record identifies which are wired and verified. Only the engineer-customizable Tender Manager is initialized. Every other employee profile is generated for actual work, belongs to one Tender and has immutable versions. Names, titles, roles and personalities are display and professional instruction data, never routing or permission keys. There is no default roster, role enum or fallback employee template.

### Profiles and planning records

`staff_models.py` owns `Personality`, `ManagerProfile`, `ManagerProfileEdit`, `StaffProfileDraft`, `StaffWorkOrder`, server-only frozen `ManagerCreationContext`, and `OfficeConflict`. The public edit/draft models reject extra properties. The server supplies all IDs, creation lineage, versions and timestamps. `ManagerCreationContext {tender_id,run_id,manager_profile_version,scope_id}` is constructed by the active Manager controller, never from model/HTTP arguments. Its scope ID records lineage and grants nothing.

`ManagerProfileService` initializes one neutral Manager in the main database, preserves every version, and uses `expected_version` for atomic edits. New runs capture the chosen version at admission, including a conversation that continues into engineering; ongoing work retains that version. Editing a personality changes neither source permissions nor AI account/model/billing/spending authority.

`StaffStore` owns generated profiles, immutable work orders and creation/revision receipts. `create_generated(context,profile,work_order,idempotency_key)` validates current same-Tender source references, then saves the complete profile and work order together. `revise_generated` uses an exact expected profile version. Existing work orders keep their original profile version. An identical receipt replay returns the original snapshot, including after the creation run finishes; an altered body conflicts. New mutations require an active queued/running creation run. No staff are created by GET or service initialization.

Store schema initialization uses individual statements inside `Repository.atomic()`. All mutations compose with an outer transaction. Creation/revision tools append their actual event in that same transaction. A committed profile is initially planned; it does not imply a provider call, a completed assignment or granted capability.

### Delegation authority and execution identity

Dynamic execution requires an explicit reviewed delegation envelope. Existing exact-task approvals acquire no new delegation power. Reading a review grants nothing. The displayed envelope and every material field participate in the plan-review fingerprint and explicit approval receipt. A previous approval receipt cannot be replayed to introduce or widen delegation; a fresh current work review is required.

The envelope binds purpose, source scope, actual versioned tools, permitted draft-output kinds, maximum staff count/depth/concurrency, exact approved route options, and aggregate root spending/request/search allowances. Source scope contains exact current artifact IDs, versions and hashes, either for the reviewed Tender or a selected subset. Work-order source IDs are starting citations, not the only sources an assignment can inspect within that reviewed scope. Newly imported or revised source bytes require scope revalidation. Requested unsupported capabilities remain visible blockers; profile text cannot make them executable.

Route options retain `AIRoute` and its connection/model capability revisions, readiness, destination, billing, reasoning/output/search settings and provider-managed extras. `RouteBinding` snapshots the approved option, staff/profile/work-order identity, source/tool scope and root budget owner. Binding and dispatch revalidate current authority. The route resolver must never call the old role-based `routes_for(...,role=...)` with a generated role or silently select a Manager/fallback model. Only explicitly displayed route alternatives may be used.

The planning `creator_run_id` and active execution `root_run_id` have different meanings. A completed planning run may have created staff for a later approved work set. That delegated work set has one active root run and durable child assignment intents. Children are attributable assignments, not new independent spending allowances. Their route-specific meters retain the root `ai_usage.run_id`, using each actual model's prices and one durable aggregate request/money/search ledger. Ready independent branches overlap up to the reviewed `max_concurrency` as coroutines with one branch-owned repository connection each; an envelope with `max_concurrency=1` runs one branch per wave in creation order. Original-client accounts serialize whole assignment turns behind one per-account lock while direct API accounts overlap. Every dispatch holds an aggregate `office_usage_reservations` admission from the same root allowance (atomic compare-and-insert; a stopped scope denies with late usage recorded). Branches whose prerequisites fail are marked failed with the blocking reason; cyclic dependency chains fail fast instead of looping. A failing branch never cancels its siblings; the first failure is re-raised after the drain with completed siblings retained. Children must not be queued behind a Tender lane held by an awaiting parent. A same-account original-client operation must wait until the parent's client lease is released; its saved state must describe that wait accurately.

A dynamic execution root must be an exact root intent in its saved approval receipt, or a later explicit engineer instruction with a same-Tender `engineer` message linked to that run under the still-current approved plan/grant. Raw active runs and Manager/staff-authored messages cannot establish a fresh budget owner. Routing verifies the immutable Manager version captured for that root; an arbitrary older global version is not interchangeable. A later engineer request is a new explicit work request, while children of one request share its root allowance.

Bounded descendants are real assignments, not side records. `StaffAssignment` carries `parent_assignment_id`, `depth` and `prerequisites`. A staff `request_child_assignment` tool (a local draft mutation under the same root allowance, explicitly allowlisted in the capability catalogue with truthful write metadata) binds and queues one child through `StaffRoutingService.bind_child` and `StaffAssignmentService.queue_child`. The child keeps its parent colleague, route option, sources and budget; requested capabilities must be a subset of the parent's pinned tools; depth is enforced against the reviewed envelope (`min` with any model-supplied cap); prerequisites must belong to the same root. The reviewed envelope accepts `max_depth` 1–8; concurrency stays 1 until T009. `OfficeScheduler.spawn_child` implements the same path for server-side callers and `budget_owners` counts distinct root budgets (exactly one per root). Ownership leases support `claim` (one owner per assignment revision), epoch-fenced `transfer` with a durable transfer record, `release`, and expiry with epoch-advancing reclaim; stale publishers are additionally rejected by assignment status/revision CAS in `save_result`. The root controller drains queued children serially after each provider lease closes, so a same-account child never runs nested inside its parent's lease.

An explicit Resume action can also establish a new attempt through `office_resume_origins` and its immutable engineer decision. It retains the exact stopped instruction, current grant and original approved/message origin; it does not duplicate the engineer's dialogue. Dynamic task-button requests go through the Manager. Stop records terminal root/assignment authority synchronously before returning, while tracked provider cleanup continues; matching late usage can still be accounted for.

`PlanReview.plan_status` distinguishes proposed, approved and superseded views without parsing prose. `DelegationOptions.supported_draft_outputs` is the available catalog, separate from the selected envelope. Saving selections grants nothing; a current displayed fingerprint and explicit approval queue exactly one persisted, pinned Manager root. Staff use the existing worker `execute` operation and `StaffProviderOutput` with either a completed draft or a genuine question. A reply to the latest saved question can requeue the same assignment under the same root allowance.

Tool adapters provide a trusted invocation identity to mutation wrappers. The model supplies professional arguments, never sender/run/authority identities. Identical provider/tool replay must resolve to the same saved operation. Direct and original-client bridges expose truthful read/write tool metadata. Creating a profile or sending an internal office message is a local draft mutation; it is not a read-only tool or an external commercial send.

### Context, messages and results

Every assignment has its own mutable context, authored notes, read receipts, item bases, recipients and research state. All source/list/search/semantic/visual/business reads enforce the reviewed scope before returning data. Prompt minimization uses the same boundary: hiding a tool does not prevent leakage through a whole-Tender overview or earlier conversation. Staff receive their exact immutable profile/work order and permitted material, not another actor's complete history.

An actor source receipt identifies the assignment, source, original artifact/version/hash, locator, and actual excerpt or visual extent inspected. Receipt of a message or artifact does not mark a source read or a document reviewed. A shared excerpt can support a recipient only after an attributable inspection receipt for that exact excerpt. The Manager never unions a child's read set into its own.

`OfficeMessage` stores the actual sender/recipient identities and profile versions, assignment, kind, authored text, exact artifact references and optional reply identity. The controller infers sender from the active context and validates all same-Tender references. Only real instructions, questions, replies, findings and handoffs enter retained conversations. A rename does not rewrite an earlier speaker's identity. All exchanges remain available through bounded pagination; highlights are a presentation filter.

Delivery receipts persist per message with `delivered/acknowledged/inspected` states, inspected extent, and the request's `required_response`. Retried deliveries/acknowledgements with the same key and body replay the original receipt; changed bodies conflict. Forged `checked/accepted` claims are rejected: received never means checked. Identical questions (same normalized text, source IDs and versions) under one root share a single Manager question; different source versions stay distinct. Ownership-transfer requests persist for `work_transfer` deliveries. Message reads attach the latest `delivery_state` and `required_response` to each message; `GET /api/tenders/{tid}/office/messages/{mid}/delivery` returns the latest durable receipt, with unknown messages or messages without delivery reported as not found.

Exact staff-result handoffs transfer complete saved tables between colleagues in one Tender. `POST /api/tenders/{tid}/handoffs` accepts `TransferRequest {result_id,recipient_staff_id,purpose,expected_basis_fingerprint,idempotency_key}` and stores the exact rows with a `current` applicability mark; replaying an idempotency key with changed content conflicts. A revised source basis marks affected handoffs `needs_review`; stale rows stay readable but are labelled historical and cannot authorize publication. The recipient (or sender) reads bounded exact pages through the `read_handoff` staff tool (`handoff_id,offset,limit` with 1–50 rows) or `GET /api/tenders/{tid}/handoffs/{id}?offset=&limit=`; guessing another colleague's handoff ID fails opaquely. Each tool read stages a durable `handoff_inspected` run event with handoff ID, offset, limit, row hash and applicability; inspection never unions the sender's source-read set, renews spending, or marks a Tender source inspected. `GET /api/tenders/{tid}/handoffs?staff_id=&direction=received|sent&cursor=&limit=` lists a colleague's handoffs newest-first with counterpart names under an opaque `created_at,id` cursor; another Tender's cursor or colleague is rejected.

Step checkpoints (`step_id,input_fingerprint,outputs,remaining_dependencies`) persist per Tender root; resuming one records an attributable reuse row and requires either the same root or a shared resume lineage, plus an exact basis fingerprint — otherwise the step re-runs. External effects move `prepared→attempted→confirmed|uncertain` (first knowledge may be `uncertain`; `uncertain` reconciles to `attempted` or `confirmed`; `confirmed` is terminal); the latest state per operation key is queryable. A resumed attempt lists reusable checkpoints from its origin/previous roots in its resume receipt and first turn, labelled as pre-interruption work to verify, never fresh results.

Assignments use explicit queued/running/waiting/completed/failed/cancelled/interrupted states. Transitions validate their prior state, active root and current binding. A `StaffResult` is an immutable validated draft with its exact profile/work-order/assignment, `OfficeOutput`, authored notes, receipts and commercial/source bases. Late results after Stop, supersession or lost authority are rejected. A saved staff draft is not an accepted quantity, rate, submission or engineering decision. Only the root job owner publishes selected domain proposals with their own validated provenance, atomically with terminal state and completion events. There is no await inside authority/publication transactions.

### Event transport, API and recovery

`OfficeEventService` persists unique UUID-hex event IDs and per-Tender monotonic sequences in the main database. A state change and its event commit together. An event ID is the opaque cursor; another Tender's cursor is rejected, while unavailable/restored history explicitly requests snapshot reset. The first transport is authenticated bounded polling. It avoids long-lived database readers through reset; future streaming requires explicit reader cancellation/ownership before adoption.

Each committed staff source receipt also records `source_inspected`; no event or receipt survives a failed read transaction. Full staff, version, work-order, assignment, result, receipt and message histories have bounded page endpoints. Snapshot windows are not history offsets. Office snapshots include a service instance ID; changing instance/history resets arrival effects while preserving truthful saved state.

`GET/PATCH /api/manager-profile` expose versioned Manager customization. `GET /api/tenders/{tid}/office` returns a consistent Manager/staff/assignment/recent-message snapshot and cursor inside one synchronous read transaction. `GET /api/tenders/{tid}/staff/{id}` returns a scoped desk. `GET /api/tenders/{tid}/office/events?after=...` returns bounded pages. A separate paginated messages endpoint retains full exchange history. No public preset-based staff-creation endpoint exists. All use the existing session Authorization header, never URL tokens. Pydantic schemas and generated frontend declarations change together.

Health advertises an explicit office revision. A mismatched/reused backend cannot run the new office UI; Settings/reset recovery remain reachable. On normal startup, abandoned assignments become interrupted with durable events and no automatic worker restart. During confirmed reset recovery, no Manager/staff/event service is initialized. Executing assignments remain owned by tracked root jobs and provider leases so reset cannot overlook them.

The implemented office revision is `1`. API responses default to `Cache-Control: no-store`, preserving explicitly declared private preview caching. The renderer uses ordinary fetch cache behavior and preserves abort identity; it does not force the request-side no-store mode that failed in the tested cross-origin browser path. Database initialization serializes the persistent WAL transition using a lock beneath the application home's runtime directory; ordinary connections do not change journal mode.

The UI reconciles snapshots, ignores duplicate events, detects gaps and requests a fresh snapshot on reset. Initial/reconnect history does not replay arrival animation. Disconnection keeps last-known work visible with an accurate status. Navigation/unmount/reset aborts polling; hidden-window animation pauses without pausing backend work. Staff portraits use a stable versioned local descriptor stored with their identity in the main database, so backup/restore retains them without creating decorative Tender evidence.

Window close hides only when the native tray is available. Open Quantix restores the same session; Current work emits navigation intent without starting a task. Explicit Quit, reset completion and OS shutdown retain their deliberate shutdown behavior. Source-development service ownership requires verification as well as native service ownership. No autostart, wake lock or release packaging is added.

## Factory reset (2026-09-09)

[Factory reset](design/factory-reset.md) defines a deliberate Settings **Reset and close** action. It erases the owned application home and its home-scoped protected credentials. It never accepts a deletion path from the renderer, erases original/export locations outside the home, or silently retains an external backup. Automated verification uses disposable roots and fake credential adapters; the engineer confirms any reset of their populated workspace.

- GET `/reset/preview` returns `ResetPreview {supported,home,tender_count,artifact_count,account_count,backup_count,blockers,fingerprint}`. The fingerprint binds the presented workspace state, excluding incidental log writes.
- GET `/reset/status` returns `ResetStatus|null`; status contains `reset_id,state,detail,credentials_cleared,fingerprint`. No credential-target inventory is public.
- POST `/reset` accepts `ResetRequest {fingerprint,confirmation:"RESET"}` and returns `ResetReceipt {reset_id,state,detail}`. Repeating an accepted fingerprint returns its original receipt; an explicit retry can resume incomplete credential cleanup. A stale initial preview or active workspace work blocks confirmation.
- Health advertises `factory_reset` only with a supported cleanup adapter and adds defaulted `reset_pending:false`. The native read-only `reset_support` command must independently succeed before the renderer can confirm reset. Missing support keeps the feature unavailable on an older desktop executable.
- Once confirmation is durably admitted, domain requests are blocked. Health/reset/diagnostic-status/shutdown remain available. Existing domain requests and background work must not race admission. Recovery does not create ordinary workspace services or automatically start queued work.

`pending-reset.json` uses format 1 and retains exact owned home, reset ID, fingerprint, confirmed timestamp, credential-target metadata, credentials-cleared state, and a fixed public detail. Public `state` matches journal `phase`: `cleaning_credentials|credential_error|ready|deleting|failed`. Inventory is durable before deleting credentials; errors preserve it. Native `finish_reset(reset_id)` accepts only the matching normal-home journal with cleared credentials and a filesystem-ready phase. A separate early native helper waits for application/service handles and the workspace lock, deletes without following links, and removes the journal only after complete cleanup. Failed cleanup remains recoverable. Startup recovery precedes opening home logs or desktop WebView files.

The original database, files, account profiles and browser state are deleted offline after the current application closes. A new launch creates empty defaults. The empty workspace coordination lock may remain; it contains no user data.

## Approved redesign contract transition (2026-09-09)

[Workspace redesign](design/workspace-redesign.md) is the current implementation authority. It replaces the composer busy prohibition below with one server-owned pending instruction, replaces the old plan/team multi-step approval with read-only fingerprinted review plus atomic explicit approval, and organizes the renderer using HashRouter. The superseded sections below remain historical; current DTOs are generated from the implemented Pydantic schemas. Health adds `workspace_revision=1`; a missing or different revision cannot operate the new workspace. Settings stays available for recovery. No legacy authority is renewed just because an account/model name matches.

Pending work is separate from accepted dialogue. A second submission cannot silently replace the one waiting message. Edit/cancel/confirm bind to that pending identity; automatic dispatch requires successful completion of its full preceding work set and fresh authority validation. Failure, Stop, restart and restore require explicit confirmation. No `await` is allowed inside authority/publication database transactions, including schema initialization.

Plan review prepares no permissions. Its displayed snapshot includes source basis, exact routes and specialist controls, account authority, billing/approved alternatives and spending. Approval revalidates the displayed fingerprint, renews only displayed permissions, approves scope and saves task run intents in the same transaction; scheduling follows commit. Readiness/catalog observations are distinct from credential/destination/billing authority changes. Routine decision note is optional; the explicit click has an accurate audit description.

Unrelated new catalog models leave existing approved routes intact. ### Conversation and waiting instruction API

- GET `/tenders/{id}/messages?limit=50` returns `MessagePage {items,next_cursor}` containing the newest bounded engineer/Manager dialogue, in chronological order. The opaque cursor fetches strictly older rows, remains stable across new appends and is scoped to its Tender. The unpaginated internal history still retains system/import records for Activity.
- `Message.result_links` contains `{kind:plan|finding|task|output,id,title,target}` derived only from exact persisted run relations. Targets are local record routes. The renderer groups repeated result kinds and keeps individual links available on demand; source citations remain separately collapsed.
- POST `/tenders/{id}/messages` accepts `MessageRequest {content,idempotency_key?,action?:review_documents}` and returns `MessageSubmission {outcome:immediate,run}` or `{outcome:pending,pending}`. An explicit action bypasses classification; all freeform text uses the bounded same-approved-AI routing pass. Engineering continuation shares the same run ID, request allowance and spend meter. Pure conversation publishes only its reply and next action, never domain proposals.
- GET `/tenders/{id}/pending-message` returns the one current `PendingInstruction|null`. PATCH accepts `{pending_id,expected_revision,content,action?}`; DELETE accepts a JSON body `{pending_id,expected_revision}`. POST `/pending-message/confirm` accepts the same identity/revision and explicitly sends held text after fresh checks.
- Submission receipt, waiting text changes and eventual consume are atomic. Old/edited/cancelled receipt IDs cannot resolve to a different new message. Readiness, credentials, route permission and spending are rechecked before consume; failures preserve the waiting instruction. Any failed/cancelled/interrupted work on its Tender holds it, including work queued later. Startup/restore never starts waiting instructions automatically.
- Resume supports the conversation run type through a fresh first pass and current preflight, without duplicating the engineer message or replacing the original receipt. Routing and engineering share one run; a stopped first pass cannot launch engineering. Outstanding unreported usage remains reserved/uncertain.

## Manager activity and send availability

The Manager composer reflects the existing single Tender work lane: any queued/running import, search-index, Manager or specialist run prevents sending another instruction, while its draft remains editable. The server remains authoritative for races. Obsolete busy-conflict notices clear when work state changes; unrelated errors and unsent edits remain visible.

Trusted source-tool and worker lifecycle events may update the existing `Run.detail` through `Repository.update_active_run_detail(run_id, detail)`. Updates are atomic and apply only to queued/running runs; they never change terminal status, invent percentage completion or claim reviewed coverage. Grok model-round observations contain bounded numeric counts. Provider failures retain only allowlisted categories/status codes and fixed messages, with a generic fallback when the client supplies no usable classification. The Settings "Methods" section and the Work "method library" are gone. `StaffProfileDraft.requested_skill_ids` is removed; profiles and definitions saved earlier load with that field ignored.
- **Kept.** The internal Quantix MCP bridge that lets the original Codex and Grok clients call Quantix tools is unchanged: it is how subscription routes work, not an extension system. The original clients' own skills, plugins and MCP features stay switched off in their configuration.
- **Tool fence.** `dispatch`/`invoke` no longer take `extra_allowed`; a staff call outside the reviewed tool grant is refused with its tool name.
- **Stored data.** Existing databases keep their now-unused tables and the defaulted `skills_json`/`extensions_json` binding columns; nothing reads or writes them. Delegation envelopes no longer serialize `skills`, so grants saved before this change would need a fresh review (none existed).
