# Run one local Quantix Host over self-contained Tender Stores

Quantix v0 is a Windows-first Electron desktop application with one sandboxed React renderer, one trusted TypeScript Quantix Host in Electron's main process, and one writer for the Engineer User's `~/.quantix` application home. We chose this over Tauri, a local web server, separate application services, or a shared database because it keeps the already-required TypeScript, Codex, and Python runtimes behind the fewest process and storage seams while preserving a secure renderer, independently recoverable Tenders, and durable local control.

## Consequences

- Electron Forge packages the application and native dependencies. The renderer runs with sandboxing and context isolation, exposes no Node integration or remote content, and can invoke only a narrow validated preload Interface; Electron security fuses disable unnecessary runtime privileges. Domain Modules remain Electron-independent even though the application Host executes in the main process.
- Windows is the only packaged and validated v0 target. macOS and Linux packaging and support are deferred rather than hidden behind speculative platform abstractions. Exactly one application instance owns `~/.quantix`; a second launch activates it instead of creating another writer.
- First-run Quantix Setup creates and validates `~/.quantix`, initializes non-secret installation state, checks local device protection, and uses a bundled `uv` binary to install the exact locked Docling runtime and prefetched models below that root. The signed application bundles a version-matched Codex binary; Codex continues to own ChatGPT authentication, configuration, and thread storage outside `~/.quantix`.
- The application home contains `installation.sqlite`; isolated `tenders/<tender-id>/` directories with `tender.sqlite`, content objects, run work, and staging; and application-wide Docling runtime/model, backup, export, log, and trash directories. The installation catalogue is rebuildable, while non-secret settings, backup records, and deletion receipts are installation facts.
- Each Tender Store is a self-contained source of truth. SQLite is accessed through `better-sqlite3` and stable Drizzle from one Host writer, with foreign keys, WAL, a defined busy timeout and synchronous policy, integrity checks, and online backup. XState v5 defines transition grammar and guards but never becomes the canonical workflow database or sole record of completed work.
- Registered Source Artifact and Artifact Version bytes are streamed into a per-Tender `cacache` implementation configured for SHA-256. SQLite stores the resulting digest, size, media type, provenance, and logical version; the cache index is not domain state, and connected Tender Package paths are no longer required after intake.
- One deep Tender Store Module owns publication. It finishes and verifies a content write before one SQLite transaction registers the immutable version, advances the current pointer, and appends its Audit Event. A crash can leave an unreferenced object for later reconciliation, but a committed record can never reference unfinished bytes. Denied and failed attempts append audit-only events without changing domain state.
- Audit Events form an immutable per-Tender sequence whose RFC 8785 canonical payload, preceding hash, and current hash are protected with SHA-256; database triggers reject update and deletion. Verified backups and archives anchor the event count and chain head. This is tamper-evident against selective mutation, not tamper-proof against a malicious administrator who controls every local file, so v0 adds no blockchain, signing infrastructure, or audit server.
- Execa supervises one long-running local `codex app-server` over stdio and one disposable official Docling CLI process per parsing attempt. Both receive staged inputs and candidate-output locations only; neither can write SQLite or canonical objects. Quantix uses the official generated Codex schema and validates Docling JSON before registration instead of inventing a Python daemon, parser protocol, process manager, localhost port, or plugin runtime.
- Startup obtains single-instance ownership and reconciles persisted operations before accepting work. SQLite rolls back incomplete transactions, unpublished staging remains noncanonical, proven unreferenced objects may be cleaned, an interrupted Docling job becomes a failed attempt, and only the exact recoverable Codex turn may resume. An unresolved provider outcome becomes an Indeterminate Agent Run in Recovery Quarantine; commands, approvals, side effects, and new provider turns are never replayed silently.
- Opening a Tender performs a quick database check and verifies its Audit Event chain. Content is verified on registration and read; full relevant integrity and digest verification precedes Tender Backup, Portable Tender Archive creation, Tender Recovery, permanent purge, and Submission Package release. v0 provides an explicit Tender Integrity Verification action rather than hidden background scanning.
- Any database, audit-chain, or registered-content integrity failure places the Tender in read-only Recovery Required and blocks canonical work, approvals, valid-backup claims, and release. Quantix preserves diagnostics and permits only EITL-controlled recovery from a verified Tender Backup or explicit whole-Tender purge; it never silently repairs, substitutes evidence, removes history, or continues with partial trust.
- `better-sqlite3` online backup and streaming `zip.js` ZIP64 archives create verified self-contained Tender Backups and Portable Tender Archives. Archives contain a versioned canonical manifest, database digest, referenced content digests and sizes, Audit Event count, and chain head; portable archives use AES-256 by default with an Engineer-supplied password Quantix does not retain. Restore verifies into staging before publish, blocks identity collisions, and never merges or overwrites; replacement is a separate EITL-controlled Tender Recovery with a verified pre-replacement backup.
- Archive is a reversible read-only Tender state. Approved deletion moves the complete store into Quantix Trash; permanent purge is a separate EITL decision, leaves a minimal installation-level Deletion Receipt, and is never automatic. Canonical records, revisions, Audit Events, backups, and quarantined failures are not silently pruned; successful scratch and proven unreferenced objects may be cleaned, while redacted operational logs rotate after at most 30 days.
- Live Tender confidentiality relies on the Windows user account, restrictive local permissions, and device encryption, with a visible warning when protection cannot be verified. v0 does not add SQLCipher or custom object encryption whose automatically available local key would not protect against the same signed-in user. Portable Tender Archives are encrypted by default when leaving that protected store.
- Every intake, archive, parser job, Agent Run, output, and storage operation has explicit non-overridable Safety Limits for bytes, entries, expansion, nesting, time, memory, output, and free disk. Exceeding a limit publishes no partial state and is audited; EITL cannot turn a safety violation into permission.
- Signed Windows updates require explicit Engineer approval, no active Agent Run, and a verified backup when stored data may be affected. Each build supports exactly one Tender Store schema and fails closed on mismatch; v0 carries no general migration framework, compatibility reader, or fallback path, and any future incompatible release affecting real Tenders requires its own decision before release.
- Quantix directly reuses mature focused libraries—Electron, Forge, React, Vite, XState, SQLite, `better-sqlite3`, stable Drizzle, `cacache`, Execa, Zod, Pino, `uv`, Docling, `zip.js`, and RFC 8785 canonicalization—but owns its Tender domain commands, EITL and permission rules, renderer Interface, relational schema, content/transaction coordination, Codex and Docling adapters, audit row rule, archive manifest, recovery decisions, and Safety Limits. Whole applications remain evidence rather than foundations, and another process, Adapter, or database is added only after a real second implementation or measured failure creates a genuine seam.
