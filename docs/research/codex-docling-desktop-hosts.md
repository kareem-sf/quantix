# Codex and Docling desktop-host research

**Issue:** [#19](https://github.com/kareem-sf/quantix/issues/19)

**Evidence snapshot:** 2026-08-06

**Current decision:** The Engineer User cancelled the packaged comparison and selected Tauri 2 with a genuine Rust Host on 2026-08-07; this report remains evidence for the Codex, Docling, and process-supervision consequences recorded in [ADR 0009](../adr/0009-run-one-local-host-over-self-contained-tender-stores.md).

**Scope:** Compare an Electron/TypeScript Host with a Tauri 2/Rust Host for packaging and supervising one Codex app-server and disposable Docling jobs on Windows, macOS, and Linux. This report does not replace ADR 0009.

## Conclusion

Both desktop hosts can implement the required topology without a long-lived Node, Python, HTTP, or WebSocket helper. They can package the same native Codex executable, launch it over local stdio, and launch each Docling conversion as a disposable child process. Docling's Python, native-wheel, and model-distribution burden is effectively identical for both.

For this slice of Quantix v0, **Electron with a TypeScript Host has the smaller and better-supported integration boundary**:

- Codex can generate version-exact TypeScript definitions from the packaged executable. OpenAI does not publish a supported standalone Rust app-server client crate; its Rust client and protocol crates are internal workspace packages with path dependencies.
- Node's child-process APIs give the TypeScript Host bidirectional stdio directly, and the already-selected Execa dependency adds a maintained, cross-platform best-effort descendant-termination facility.
- Electron can copy native executables outside ASAR as ordinary application resources, then sign those nested binaries with the application.

Tauri 2 with a Rust Host is feasible and still deserves the equivalent packaged prototype required by the parent investigation. Its disadvantage here is not Rust itself. It is the additional integration code currently required:

- consume Codex's generated JSON Schema and maintain or generate a Rust JSONL/JSON-RPC adapter;
- add a process-tree supervisor beyond `tauri-plugin-shell`, whose `kill` operation terminates the direct child but does not guarantee descendant termination; and
- produce target-triple-suffixed sidecar layouts.

The strongest result is a **common release gate**, not a host winner: current OpenAI documentation says `codex app-server` is primarily for development and debugging and may change without notice; its app-server command and WebSocket transport are experimental and unsupported for production workloads. Quantix may use a pinned version in a prototype, but ADR 0009 must not describe this interface as a supported production contract until OpenAI provides that assurance or the project explicitly accepts the experimental dependency.

Accordingly, issue #22 should carry forward Electron/TypeScript as the provisional lower-complexity choice for Codex and Docling integration, while treating the packaged, signed, three-OS prototype and the OpenAI support question as decision gates. This report alone does not authorize changing ADR 0009.

## Equivalent topology under test

The comparison is only meaningful if both prototypes use the same boundaries:

```text
renderer (untrusted UI)
        |
        | narrow typed commands and events
        v
trusted desktop Host
        |-- one pinned codex app-server process
        |     local stdin/stdout JSONL only
        |     Codex owns ChatGPT authentication
        |
        `-- zero or more disposable Docling processes
              one process per job
              staged input -> staged candidate output
              pinned uv/Python/environment/models
```

The renderer must not receive general shell access. It requests domain operations from the trusted Host. The Host owns executable resolution, environment construction, process lifetime, protocol validation, logging, interruption, and reconciliation. Neither option needs a local web server, an embedded daemon, a Node sidecar, or a persistent Python service.

| Variable | Fixed prototype value |
| --- | --- |
| Codex | The same exact release and native target binary in both packages |
| Codex transport | Local stdio JSONL; no WebSocket transport |
| Codex API | Stable fields generated by the packaged binary; no experimental fields |
| Authentication | The engineer's existing Codex/ChatGPT sign-in; Codex owns tokens |
| Docling | The same exact Docling, uv, Python build, lock, models, CLI arguments, and test corpus |
| Conversion | CPU-only standard PDF pipeline for the portable v0 baseline |
| Process model | One app-server plus disposable one-shot Docling children |
| Targets | Packaged Windows, macOS, and Linux builds on real target machines |
| Updates | Host, Codex executable, runtime manifest, schemas, and compatibility tests versioned as one release contract |

## Codex app-server findings

### Product status is a release gate

OpenAI describes app-server as the interface used by rich Codex integrations for authentication, conversation history, approvals, and streamed events. That capability is a closer fit than the TypeScript SDK, which OpenAI positions for programmatic automation and CI. However, the current [Codex CLI command reference](https://learn.chatgpt.com/docs/developer-commands?surface=cli) explicitly describes `codex app-server` as primarily a development/debugging surface that may change without notice. The [app-server guide](https://learn.chatgpt.com/docs/app-server) also labels the command and WebSocket transport experimental and unsupported for production workloads.

The guide's “stable” protocol subset is therefore a less volatile subset of an experimental command, not a production-support guarantee. Pinning a release, generating its schemas, and avoiding experimental fields reduces compatibility risk but does not remove that product-status risk.

### Packaging is equivalent

The current OpenAI Codex release publishes native artifacts for Windows x64/arm64, macOS x64/arm64, and Linux musl x64/arm64, including full Codex executables and dedicated app-server artifacts. The official [npm package build script](https://github.com/openai/codex/blob/main/codex-cli/scripts/build_npm_package.py) maps those target-specific executables into six platform packages. The [0.146.1 release](https://github.com/openai/codex/releases/tag/rust-v0.146.1) is the evidence snapshot used for this report, not a version recommendation.

Both desktop packages should include an exact native Codex executable for their target rather than install Codex from npm during first run. Before choosing the smaller dedicated app-server artifact, the prototype must prove it includes every helper needed by Quantix's actual workflow. Otherwise package the corresponding full Codex artifact. Record its upstream release, digest, license material, and generated-schema digest in the application manifest.

The shell technology does not change this payload. Electron places it in an unpacked application resource; Tauri declares it as an external binary with the appropriate target-triple filename.

### Protocol and generated bindings favor TypeScript

The [app-server guide](https://learn.chatgpt.com/docs/app-server) establishes this local sequence:

1. Spawn `codex app-server`; its default transport is newline-delimited JSON on stdin/stdout.
2. Send `initialize` once per connection, then the `initialized` notification.
3. Start or resume a thread, start a turn, and process streamed notifications.
4. Send `turn/interrupt` to request graceful cancellation and wait for `turn/completed` with an interrupted status.

The messages use JSON-RPC 2.0 shapes while omitting the `jsonrpc` member. The packaged executable can emit its exact interfaces with:

```text
codex app-server generate-ts --out <directory>
codex app-server generate-json-schema --out <directory>
```

Generation excludes gated experimental fields unless `--experimental` is explicitly selected. Quantix should generate and commit or package the stable output from the exact executable used by that release and fail its build if generation drifts.

For Electron, generated TypeScript is a direct fit for the trusted TypeScript Host. The official [`@openai/codex-sdk`](https://github.com/openai/codex/blob/main/sdk/typescript/README.md) also demonstrates OpenAI's supported Node/JSONL integration path, but it is not a substitute for app-server's interactive authentication, approvals, history, and event contract.

OpenAI's repository contains `codex-app-server-client` and `codex-app-server-protocol` Rust workspace crates, but they are internal packages: their versions are workspace `0.0.0`, they use repository-local path dependencies, and OpenAI does not publish them as a supported standalone client surface. A Rust Host should therefore use the generated JSON Schema as its public source of truth and own a narrow protocol adapter. Pulling OpenAI's internal crates by Git URL would import substantial private workspace coupling and violate Quantix's preference for durable, established dependencies.

### Authentication must remain owned by Codex

The [Codex authentication documentation](https://learn.chatgpt.com/docs/auth) supports signing in with an existing ChatGPT subscription. Codex persists and refreshes its own credentials, normally in `~/.codex/auth.json` or the operating-system credential store according to `cli_auth_credentials_store`; the CLI and other Codex clients share that state.

Quantix must not copy, parse, migrate, encrypt, or refresh those tokens. On startup the Host asks app-server for `account/read`. If sign-in is absent, it may invoke app-server's login flow and open the returned authorization URL for the engineer. `CODEX_HOME` should remain the engineer's existing Codex home unless the engineer explicitly chooses an isolated Codex profile. Codex-owned authentication is not Quantix application state and should not be moved into `~/.quantix` merely to satisfy Quantix's storage convention.

This contract is identical in Electron and Tauri. Automated CI may use a deterministic fake JSONL fixture. A real authenticated smoke test is opt-in on an engineer's machine and must never export or log credentials.

### Interruption and crash recovery need a Host supervisor

`turn/interrupt` is the correct first-stage cancellation mechanism because it lets app-server reach a terminal turn state. It is not a process-tree primitive. The current protocol exposes experimental background-terminal list/clean/terminate methods, but the stable-only client cannot rely on those APIs. A command spawned during a turn can therefore outlive the logical interruption unless the Host also supervises the operating-system process tree.

The required normal shutdown sequence is:

1. Persist shutdown/cancellation intent in Quantix state.
2. Send `turn/interrupt` for an active turn.
3. Wait for its terminal notification within a bounded grace period.
4. Close app-server stdin and wait for the direct child.
5. Escalate to process-tree termination when the grace period expires.
6. Reconcile durable thread and turn state before accepting more work.

App-server supports reading and resuming stored threads, but the public documentation does not guarantee that an in-flight turn survives app-server or Host death. A lost connection during an active turn must be recorded as **indeterminate**, not automatically replayed. After restarting the exact executable, Quantix reads/resumes the thread, reconciles the last durable events, quarantines unverified outputs, and requires engineer-in-the-loop disposition when it cannot prove a terminal state. Automatic replay could duplicate commands, files, messages, or approvals.

The [Codex sandbox documentation](https://learn.chatgpt.com/docs/sandboxing) describes platform-native confinement for commands Codex launches: Seatbelt on macOS, native Windows sandboxing, and bubblewrap-based Linux/WSL behavior with platform caveats. It does not sandbox the app-server process itself or a Docling process launched separately by Quantix. The Host must not represent renderer sandboxing, Tauri capabilities, or a staged working directory as equivalent to operating-system confinement of those children.

## Desktop-host process supervision

### Electron with a TypeScript Host

Electron's trusted main process can use Node [`child_process.spawn`](https://github.com/nodejs/node/blob/main/doc/api/child_process.md) for the exact bidirectional pipe required by app-server. Electron's `utilityProcess` is not the right abstraction because it does not provide an equivalent piped stdin contract. Codex and Docling should be normal native children of the main process with `windowsHide` enabled and explicit stdin/stdout/stderr policies.

The existing Execa dependency is a useful deep module over Node process details. Its [termination contract](https://github.com/sindresorhus/execa/blob/main/docs/termination.md) supports `killDescendants: true`: it uses process-group behavior on Unix and `taskkill` on Windows to make best-effort descendant cleanup. The contract is not absolute. A Unix descendant that creates a new session can escape the group, and no JavaScript cleanup hook runs if the Host is itself forcibly killed. `gracefulCancel` is only cooperative for Node children, so Codex cancellation must still begin with `turn/interrupt`, and Docling must use ordinary signal/timeout escalation.

Consequently, Electron needs no custom JSONL daemon or routine tree-walking implementation, but it may still need a small OS-backed containment layer for the strongest crash invariant:

- Windows: place children in a Job Object configured to terminate members when its supervising handle closes.
- macOS/Linux: validate a process-group or small parent-death wrapper against abrupt Host death and descendants that re-parent or create sessions.

That crash-hard requirement must be identical in the Tauri prototype; it should not be silently weakened to favor either host.

Electron resources declared with `extraResource` are copied into `Contents/Resources` on macOS and the application `resources` directory elsewhere. Resolve them from `process.resourcesPath`. The [ASAR documentation](https://www.electronjs.org/docs/latest/tutorial/asar-archives) warns that executable subprocess behavior from within ASAR is limited; native sidecars must stay unpacked rather than depend on temporary extraction.

### Tauri 2 with a Rust Host

Tauri's official [sidecar guide](https://v2.tauri.app/develop/sidecar/) supports external binaries on Windows, macOS, and Linux. Each declared binary is stored with a `-$TARGET_TRIPLE` suffix, and the Rust `tauri-plugin-shell` API can spawn it, stream stdout and stderr events, and write stdin. Keeping all process creation in trusted Rust avoids granting the renderer a generic shell capability. If the renderer ever invokes shell-plugin commands directly, Tauri's capability scopes must enumerate the exact command and allowable arguments.

The plugin provides the necessary pipe, but not the complete supervisor. Its current [`CommandChild::kill` implementation](https://docs.rs/tauri-plugin-shell/latest/src/tauri_plugin_shell/process/mod.rs.html) targets the direct child. Tauri's [#11686](https://github.com/tauri-apps/tauri/issues/11686) records a Windows case where Python/PyInstaller descendants remained after `kill`; it was closed without adding descendant termination to the plugin. The earlier [#4949](https://github.com/tauri-apps/tauri/issues/4949) discussion likewise distinguishes direct-child termination from killing grandchildren.

The Rust Host therefore needs a separate, mature process-group/Job-Object dependency or a narrow platform module. It must demonstrate graceful protocol cancellation, bounded escalation, descendant cleanup, and abrupt-parent-death behavior on all three targets. Reimplementing process enumeration and recursive killing in Quantix would be the wrong boundary.

Tauri capabilities protect calls from the renderer into the Rust core. Once trusted Rust starts Codex or Docling, those processes have the permissions supplied by the operating system; capabilities do not sandbox them.

### Process-supervision comparison

| Requirement | Electron / TypeScript | Tauri 2 / Rust |
| --- | --- | --- |
| Codex bidirectional stdio | Native Node `spawn`; mature | `tauri-plugin-shell` or `std::process`; mature pipe primitives |
| Version-exact protocol types | Direct generated TypeScript | Generated JSON Schema plus maintained/code-generated Rust adapter |
| Direct-child interruption | App-server protocol, then Execa/Node escalation | App-server protocol, then plugin/Rust escalation |
| Descendant termination | Execa provides reusable best-effort cross-platform behavior | Plugin does not provide it; select an additional Rust dependency/platform module |
| Cleanup after abrupt Host death | Needs validated OS containment beyond JS exit hooks | Needs validated OS containment; Rust ownership alone is insufficient |
| Renderer isolation | Narrow Electron IPC; no Node in renderer | Narrow Tauri commands/capabilities; no shell access in renderer |
| Native sidecar layout | Unpacked `extraResource` resolved from resources path | `externalBin` with one target-triple-suffixed file per target |
| Extra long-lived helper | None | None |

## Docling and uv findings

### There is no official standalone Docling executable

Current [Docling installation documentation](https://docling-project.github.io/docling/getting_started/installation/) supports Python on Windows, Linux, and macOS for x86_64 and arm64. Docling is nevertheless a Python application with PyTorch and platform-native wheels, not an official single-file cross-platform binary. Packaging it requires the same decisions regardless of the desktop shell.

For Quantix v0, the simplest durable distribution is:

1. Bundle an exact target-specific [uv standalone binary](https://docs.astral.sh/uv/getting-started/installation/) with the desktop application.
2. During explicit first-time setup, install an exact uv-managed CPython build under `~/.quantix`, synchronize an exact locked Docling environment, and prefetch the exact model set.
3. Verify staged runtime files and record a runtime manifest before atomically activating them.
4. During tender work, launch the environment's actual Docling CLI directly. Do not run `uv sync`, resolve packages, download models, or update components in the job path.
5. Treat an application update and its required runtime-manifest transition as one coordinated release, even though the runtime itself remains under `~/.quantix`.

uv's [managed-Python documentation](https://docs.astral.sh/uv/concepts/python-versions/) uses self-contained `python-build-standalone` distributions because Python does not publish official portable binaries. [`uv sync --locked`](https://docs.astral.sh/uv/concepts/projects/sync/) enforces a checked lock rather than silently changing it. Quantix should pin the uv release, CPython build, environment lock, model manifest, and artifact hashes. uv only guarantees lockfile-schema compatibility within its documented compatibility window; the setup process must not float the uv executable.

Relevant state can be routed with `UV_PYTHON_INSTALL_DIR`, `UV_CACHE_DIR`, and `UV_PROJECT_ENVIRONMENT`; `UV_PYTHON_CPYTHON_BUILD` can pin a managed CPython build. The Host must construct those paths itself under `~/.quantix` and never accept arbitrary renderer-supplied environment variables or executable paths.

Bundling the complete Python/PyTorch/Docling environment inside every desktop artifact is another feasible prototype variant, but it increases package size, code-signing/notarization surface, native-wheel variants, and update churn. Docling offers no official artifact that removes that complexity. A first-run pinned setup is smaller, while creating a supply-chain responsibility for downloaded executable code; hashes, provenance, license inventory, and an SBOM are therefore part of activation, not optional paperwork.

### Real cross-platform behavior has a macOS Intel exception

Docling's official installation page documents a special macOS Intel path: newer PyTorch releases no longer provide Intel Mac wheels, so that target requires older pinned PyTorch/torchvision versions and Python no newer than the supported combination. A nominally cross-platform lock does not prove binary availability on that target.

The prototype must therefore build and execute the real lock on every supported OS/architecture. Quantix should establish CPU-only conversion as the v0 portable baseline. GPU acceleration can be a later, explicitly platform-specific capability; promising equivalent CUDA, Metal, and other accelerator behavior would introduce unnecessary v0 variance.

### Models and CLI execution must be offline and deterministic

Docling normally downloads models on first use. Its [advanced-options documentation](https://docling-project.github.io/docling/usage/advanced_options/) supports prefetching models with `docling-tools models download` and locating them with `--artifacts-path` or `DOCLING_ARTIFACTS_PATH`. Quantix setup should prefetch the selected model manifest into `~/.quantix/models/docling`, then the job runner should use that exact path.

The current [Docling CLI reference](https://docling-project.github.io/docling/reference/cli/) uses the `docling convert` command. It exposes JSON output, output directories, artifact paths, document timeout, thread and device controls, and switches for remote services and external plugins. The disposable job contract should use:

- one staged input and one unique candidate-output directory;
- `docling convert` with the pinned artifact path and JSON output;
- remote services disabled and external plugins disabled;
- a bounded document timeout, CPU device, and bounded thread count;
- abort-on-error behavior and strict exit/output validation.

Disabling remote services and plugins reduces Docling's behavior surface, but it is not an OS sandbox. Docling still runs with the filesystem and network rights of the user unless Quantix adds platform-specific confinement. Passing only staged paths is a least-authority application contract, not proof that the process cannot access other paths.

### Docling recovery is disposable, not resumable

Docling documents no conversion checkpoint/resume protocol. The Host should never publish directly into canonical tender content. It writes to a unique staging directory and promotes validated output only after a clean exit and schema/content checks. A timeout, signal, Host crash, missing terminal record, or malformed output marks that attempt failed or indeterminate; the candidate directory is quarantined or safely removed and a new attempt is scheduled only under the workflow's retry and engineer-approval rules.

This recovery model is identical for Electron and Tauri. The Host technology cannot make an in-process Python conversion transactional.

## Packaging, signing, and updates

### Electron

Electron's [code-signing guide](https://www.electronjs.org/docs/latest/tutorial/code-signing) covers Windows signing and macOS signing/notarization. Packaged Codex and uv binaries, and any fully bundled Docling native files, are nested executable content and must be present before signing. Electron Packager's macOS signing configuration supports signing additional binaries; the release pipeline must verify the final installed paths and signatures rather than assume the outer application signature is enough.

Electron updater artifacts include declared application resources. A runtime later installed under `~/.quantix` is outside that artifact and requires the common runtime-manifest reconciler described above.

### Tauri

Tauri's [updater documentation](https://v2.tauri.app/plugin/updater/) creates signed platform update artifacts, and declared `externalBin` files are part of the application bundle. They must exist for each target before platform signing/notarization and updater signing. As with Electron, an externally installed `~/.quantix` Docling runtime is not automatically replaced by the desktop updater.

### Common safe-update sequence

Neither updater should replace a running Codex or Docling executable. The Host must:

1. refuse a new update while an approval or irreversible workflow transition is active;
2. persist update intent;
3. gracefully interrupt Codex and stop accepting Docling work;
4. drain or terminate children using the tested supervisor;
5. install a signed desktop update containing the matching Host, Codex binary, and protocol schemas;
6. stage and verify any required `~/.quantix` runtime transition;
7. restart, validate component versions, and reconcile indeterminate work before resuming.

Current user reports are sufficient reason to test this sequence aggressively, but they are not primary API guarantees: Codex issue [#11090](https://github.com/openai/codex/issues/11090) reports orphaned app-server descendants after a macOS client quit; [#12382](https://github.com/openai/codex/issues/12382) reports stale resume behavior after an unclean active-turn shutdown; [#35782](https://github.com/openai/codex/issues/35782) reports Windows disconnect/recovery failure; and [#32037](https://github.com/openai/codex/issues/32037) reports an update interacting with a running app-server. These reports shape failure-injection tests, not the architecture verdict.

## Required packaged prototype

Source-level demos are insufficient. Each option must produce installable artifacts and run the same acceptance suite on Windows, macOS, and Linux, including every architecture Quantix intends to support.

### Codex acceptance cases

- Verify the packaged executable digest and generated stable-schema digest before launch.
- Initialize exactly once, issue `account/read`, and prove that Quantix never reads credential files or logs tokens.
- Start a thread and turn against a deterministic fake JSONL server in CI.
- With an engineer's opt-in existing login, run a minimal real app-server smoke test without exporting credentials.
- Interrupt an active turn and observe its terminal interrupted notification.
- Exercise a turn that creates a descendant command; verify bounded cleanup after graceful interruption, forced child termination, normal Host exit, and abrupt Host death.
- Kill app-server mid-turn, restart it, read/resume the thread, and prove the Host marks unverifiable work indeterminate rather than silently replaying it.
- Feed malformed JSONL, unknown notifications, a version/schema mismatch, a hung child, and stderr flooding; prove bounded memory and a diagnosable terminal state.

### Docling acceptance cases

- Complete first setup from an empty `~/.quantix` using only pinned, verified inputs; then repeat setup idempotently.
- Convert the same small PDF corpus offline with an already-prefetched model directory and compare normalized JSON invariants.
- Prove no dependency or model resolution occurs during a tender job.
- Cancel and time out a conversion; verify the direct child and its descendants are gone.
- Kill the Host during conversion; verify candidate output is not promoted and is reconciled on restart.
- Exercise filenames with spaces, Unicode, long paths, read-only inputs, corrupt PDFs, and output-disk exhaustion.
- Validate the macOS Intel lock independently if Intel macOS is claimed as supported.

### Packaging and update acceptance cases

- Inspect the installed application to prove Codex and uv are outside ASAR for Electron or correctly target-suffixed for Tauri.
- Verify Windows signatures, macOS nested signatures and notarization, and the selected Linux package/update authenticity.
- Install an update while children are idle, active, gracefully stopping, and forcibly hung; prove no executable is replaced while running and no work is silently duplicated.
- Roll forward from the prior runtime manifest and recover from interruption during staging. Do not add a backward-compatibility layer; retain the previous active runtime until the new one is fully verified, then switch atomically.

## Custom-code and dependency boundary

| Boundary | Electron / TypeScript | Tauri 2 / Rust |
| --- | --- | --- |
| App-server DTOs | Generated TypeScript from exact Codex binary | Generated JSON Schema plus selected Rust code generator or narrow maintained DTOs |
| JSONL framing/correlation | Small Host adapter over Node streams | Small Host adapter over Rust async/process streams |
| Process lifetime | Execa for normal and descendant handling; narrow OS containment only if crash-hard cleanup is required | Shell/process primitive plus a selected cross-platform supervisor or narrow Job-Object/process-group module |
| Docling setup | Shared manifest/state-machine logic in TypeScript; invoke bundled uv | Shared manifest/state-machine logic in Rust; invoke bundled uv |
| Docling execution | Execa direct one-shot child | Rust direct one-shot child |
| Authentication | App-server account methods; no token code | App-server account methods; no token code |
| Updater coordination | Host-level quiesce and runtime reconciliation | Host-level quiesce and runtime reconciliation |

The allowed custom code is a narrow domain-facing Host adapter and release/runtime state machine. The following would be unjustified v0 reinvention:

- a Quantix authentication/token store for Codex;
- a custom local HTTP/WebSocket bridge;
- a persistent Python/Docling daemon;
- a Node helper process beside the Rust Host;
- importing OpenAI's unpublished internal Rust workspace crates;
- recursive process enumeration implemented from scratch;
- a custom Python or model package manager; or
- a renderer-accessible general shell command.

## Decision input for issue #22

1. **Carry Electron/TypeScript forward as the provisional lower-complexity option for this subsystem.** It consumes Codex's generated TypeScript directly and already has a maintained process dependency with cross-platform descendant handling.
2. **Keep Tauri/Rust in the equivalent packaged prototype.** It can meet the topology without a helper runtime, but the prototype must identify and validate the Rust schema-generation and process-tree dependencies rather than hide those seams behind “native” claims.
3. **Treat Docling as host-neutral.** Its uv/Python/PyTorch/model, sandbox, signing, runtime-update, and recovery work exists in both architectures.
4. **Block a production commitment on the app-server support question.** Obtain an OpenAI-supported production contract or record explicit acceptance of the experimental dependency, with exact-version pinning and compatibility testing.
5. **Do not change ADR 0009 from this report alone.** Combine this evidence with the storage/process research, the Rust dependency investigation, and real signed prototype measurements before confirmation.
