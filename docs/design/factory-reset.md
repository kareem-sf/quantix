# Factory reset — 2026-09-09

User requested a Settings reset that deletes all Quantix data and returns it to a fresh installation. Architecture/local implementation/testing are already authorized by AGENTS. This implements the feature; it does not authorize the agent to erase the populated production workspace. The separate explicitly requested test-folder deletion was blocked by automatic approval review; that outside folder is never added to reset scope.

## User flow

Settings has a clear Reset Quantix section, describing all records, imported copies, outputs, AI accounts/private sign-ins, preferences/drafts, caches/software, logs and backups. Original input files, chosen exports and independent application credentials outside the Quantix home remain separate. No silent backup of data the user asked to erase. Existing backup export stays available before reset.

One dialog shows current counts and the exact application home, explains that Quantix will close and AI setup will need to be repeated, and requires typing RESET. Primary action Reset and close. Active Tender/AI setup work blocks reset with a clear instruction to finish/stop it. Confirmation is scoped to a fresh preview fingerprint; double submission returns the same receipt. Reset is supported only where the native cleanup and credential adapters are implemented; unavailable platforms/browser preview must say so.

## Contract and lifecycle

1. Authenticated GET /reset/preview -> ResetPreview: supported, home, tender_count, artifact_count, account_count, backup_count, blockers:string[], fingerprint. GET /reset/status -> ResetStatus|null. POST /reset accepts {fingerprint,confirmation:Literal['RESET']} -> ResetReceipt {reset_id,state,detail}. No user-supplied delete path. Pydantic and generated TS together. Health advertises factory_reset when supported.
2. Backend owner stages a durable home/pending-reset.json journal with exact reset ID, phase and owned credential metadata (never credential values). Under a reset admission barrier, revalidate idle state/fingerprint; reject later domain requests once confirmed. Metadata-only OS credential cleanup deletes only home-scoped Quantix AI/mail targets and known private Codex-home targets. Missing entries are success; other errors keep a recoverable failure and prohibit a false success. Grok auth is file-backed. See .superpowers/sdd/factory-reset/credentials-audit.md.
3. After credentials are removed, phase is ready. No filesystem wipe occurs through a running service request. Frontend clears its Quantix-specific draft/theme/cache state and invokes native finish_reset(reset_id). The native command validates the exact ready journal under normal ~/.quantix, launches a separate mode of its own executable before normal Tauri/logger setup, requests owned-service shutdown, and exits the UI.
4. Native helper waits for the desktop and backend workspace lock to release. It then removes home contents without following links/junctions; the journal and an empty workspace lock remain until successful cleanup. Retry transient Windows file locks within a bound; retain failure journal for retry if files cannot be cleared. Never traverse outside the verified root, accept arbitrary caller delete paths, erase originals elsewhere, or label partial cleanup complete. Once all old data is gone, remove journal; leaving an empty control lock is acceptable and contains no old data.
5. Recovery must precede logger/WebView creation. Native startup and development launchers cooperate with an already-confirmed ready/deleting filesystem reset before opening files under the root. A credential-cleanup failure can reopen a gated reset recovery UI; ordinary workspace work stays blocked until reset completes. No endless automatic relaunch loop. Open Quantix again after successful reset to create clean defaults.

## Ownership

Journal schema v1 (coordinate additions, never silently diverge): `home/pending-reset.json` contains `format:1`, `reset_id` (32 lowercase hex), `home` (exact absolute owned root), `phase:cleaning_credentials|credential_error|ready|deleting|failed`, `credentials_cleared:bool`, `fingerprint` (accepted preview), `confirmed_at`, `detail` (fixed public copy), and private `credential_targets` metadata if required. Native purge requires credentials_cleared=true and matching reset_id/home. No credential blobs. Successful purge removes the journal. Windows credential adapter is the initial verified implementation; unsupported platforms must expose supported=false instead of partial-reset success.

Native commands: read-only `reset_support -> bool`; `finish_reset(reset_id)` validates ready/deleting/failed journal (with credentials cleared), starts the same executable's reset helper mode, requests normal-root service shutdown even in development, then exits. Native helper mode precedes logging and Tauri initialization. Its CLI never accepts a caller-supplied deletion root. Isolated filesystem tests call the internal purge function with disposable roots; never target production. Startup/PowerShell/Node preflight must run before opening root log handles to complete already-confirmed ready/deleting resets; failed resets reopen gated recovery.

Backend Health adds defaulted `reset_pending:bool=false` and capability factory_reset on a supported platform. Confirmed/reset-failed workspaces allow only health/reset/diagnostic-status/shutdown requests; reject domain reads and writes. Track in-flight mutating requests so reset cannot race a mail send or another settings/domain update. Reset confirmation sets the admission barrier synchronously before credential-cleanup await. Close/cancel background clients after rejecting a busy workspace, preserving no automatic work on reset. A failed cleanup retains the journal for explicit Retry; no normal workspace use or false reset completion.

## Verification

Public state values match journal phases. `ResetStatus` contains `reset_id`, `state`, `detail`, `credentials_cleared`, and `fingerprint`; `ResetReceipt` contains only `reset_id`, `state`, `detail`. POST with the original fingerprint and typed confirmation retries an interrupted/failed credential cleanup; an already-ready journal returns its original receipt. The renderer never receives credential targets. A pending reset status can be read without constructing ordinary workspace screens. Journal inventory is durable before deleting the first credential.

Synthetic homes only for destructive tests. Verify preview/stale fingerprint/typed confirmation/busy guards; repeat request receipt; exact AI/mail/Codex ownership and missing/error credential handling without reading values; root/junction/path-escape rejection; locked-file failure and restart recovery; delete every data category and recreate zero Tenders/accounts/default preferences; preserve neighboring original files; renderer storage removal and cancellation/failure copy; no deletion of live ~/.quantix during acceptance. Native development compile/check only, no release build. Real app preview/dialog inspection is allowed, final reset is not executed by the agent.
