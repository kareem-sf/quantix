# Synthetic Tender benchmarks

The suite has 24 explicit cases: four each for BOQs, specification conflicts, drawing revision schedules, supplied market observations, supplier comparisons and integrated agent work. `cases.py` contains literal expected numbers, tolerances, units, finding codes and evidence references. Goldens are not generated by the production calculator. The 42 immutable DOCX originals in `fixtures/` contain only synthetic source facts; the manifest pins their bytes and text. Benchmarks verify them and import them normally without editing the originals.

Run from the project root with its backend virtual environment:

```powershell
# Default: validate the complete dataset and fixture bytes; no model requests.
backend/.venv/Scripts/python.exe scripts/run-agent-benchmarks.py

# Run 24 actual CalculationService probes in a separate synthetic store; no AI.
backend/.venv/Scripts/python.exe scripts/run-agent-benchmarks.py --deterministic

# Explicit live run: use one existing ready account/model and a total USD cap.
backend/.venv/Scripts/python.exe scripts/run-agent-benchmarks.py --live --connection ACCOUNT_ID --model MODEL_ID --budget 5.00

# A three-repetition pilot; this does not qualify full-suite completion.
backend/.venv/Scripts/python.exe scripts/run-agent-benchmarks.py --live --connection ACCOUNT_ID --model MODEL_ID --budget 1.00 --case boq-01

# Compare two complete retained reports. Critical regressions fail by default.
backend/.venv/Scripts/python.exe scripts/run-agent-benchmarks.py --compare --baseline BASELINE_REPORT_JSON --candidate CANDIDATE_REPORT_JSON
```

The live driver creates distinctly labelled synthetic Tenders. It uses `JobManager` for ordinary source import, `AIPolicyService` for the exact chosen route/budget, and the normal `PlanReviewService` fingerprint/approval before starting the root job. It does not copy credentials, convert OAuth credentials, fabricate readiness, switch models, enable account extras, approve real customer Tenders or bypass original-client execution. The Manager configuration, connection revision and model basis stay fixed within a run group. Config changes or incomplete usage stop subsequent paid attempts.

The CLI divides the explicit **total** budget across all selected case repetitions, rounding each per-attempt allowance down. Unused allowances are not transferred to another attempt. Conservative provider reservations can reject a small allowance before work begins; a budget never guarantees completion. Original-client subscription routes retain their normal account serialization and billing controls. Extra-spending authority is never inferred. All runtime copies, synthetic database rows, admission records, calculations, artifacts and reports remain beneath the selected Quantix home; source fixtures remain in the package.

Each case runs exactly three times. `pydantic-evals==2.40.0` owns the repeated dataset execution and evaluator report. Every attempt also has a separately persisted Quantix record, including exceptions and blocked attempts. An interrupted run retains completed/current attempts and never invents results for unstarted work. Results include task completion, evidence precision/recall, numeric accuracy, findings recall, end-to-end latency, requests, input/output tokens, estimated cost and nullable provider-reported cost/partial status. Unknown telemetry is not zero or an invoice.

Scoring reads the actual saved work-product table, exact calculation IDs, independently recomputed calculation outputs and server-recorded source reads. Correct-looking prose or a model's claim to have called a tool cannot pass. Every numeric row supplies its exact `calculation_id`; the value and source references must match that saved calculation, not an unrelated calculation with the same number. Each expected claim requires its exact supporting evidence, actually read by the Manager. Evaluator version2 additionally requires integrated results to link each numeric calculation to a different reviewer actor, that actor's completed assignment/result, the same root, an actual successful check event for that exact calculation, its ID in the handed-off result, and that reviewer's actual source-inspection receipts. Self-checks and unrelated completed colleagues cannot qualify. The collector's own `CalculationService.check` calls create separate local replay receipts for verification; those receipts are never counted as the agent's independent review.

`report.json`, `report.md`, `dataset.json`, `pydantic-evals.json` and per-attempt JSON records are saved under `~/.quantix/benchmarks/<report-id>`. Modes distinguish dataset validation, deterministic probes, injected synthetic executor/model checks and actual live jobs. No live result is claimed by unit tests. Pilot subsets and missing/uncertain usage cannot establish full-suite completion. Full comparison requires matching datasets/modes and all 72 case repetitions. `--regression-review PATH` can annotate an exact comparison with an engineer rationale; it cannot waive a critical engineering regression or make incomplete work pass.

## Adoption enforcement

The normal Manager, message classifier and staff provider paths check recorded adoption decisions before provider entry and before every actual request. They retain the full approved route identity before internal classifier or remaining-budget reductions. The fingerprint includes account revision, model capabilities/prices, generation/native-tool settings, immutable Manager version, the actual checked client/runtime version from readiness, and the shared bundled implementation/dependency fingerprint. A software update and successful recheck therefore cannot reuse earlier acceptance just because account/model revisions stayed unchanged. Unseen configurations remain usable, without a quality claim. Accepted admission, engineer review and baseline selection revalidate the actual referenced reports and hashes within their synchronous decision transaction. Missing or damaged evidence requires restoration; it cannot become an unknown configuration or an accepted comparison. SQLite guards reject updates, deletion and replacement of verified report rows.

Only the real live job driver can register a decision. The service re-collects the actual saved job, source, work-product, calculation and usage receipts and re-scores them; it does not trust uploaded report JSON or supplied score flags. The resulting `verified-report.json` and hash are retained with the decision. A completed critical case with an actual provider request and failed engineering assertions blocks that exact configuration. Infrastructure failures and missing usage do not establish model quality or acceptance. Clearing a critical block requires a complete comparable live evaluation with all 72 attempts passing.

A passing candidate is compared with the latest comparable complete live baseline. More than a 20% total increase in measured latency, requests, input/output tokens or estimated attributable cost requires explicit engineer review of the exact configuration, candidate/baseline report hashes and a rationale in AI benchmark reviews. A rise from a known zero baseline also requires review. Comparisons with any unknown metric remain explicitly unavailable; unknown values are never added as zero. The panel shows measured before/after values and loads the exact verified baseline/candidate attempts through an authenticated, hash-checked bounded endpoint. A verified report ID is immutable: identical replay leaves later decisions untouched, and changed contents require a new ID. This performance/cost review cannot override critical engineering errors. No live baseline or acceptance is invented from deterministic or synthetic model tests.

The explicit positive-budget CLI command can test a blocked configuration through a server-held admission created inside the normal plan-approval transaction. It binds one root, exact checked-in synthetic originals, case/repetition, configuration and original spending ceiling. Other roots, changed source bytes, terminal runs or widened budgets cannot reuse it. This exception does not replace account, source, plan, request or spending checks. The app imports no dev-only evaluation library during ordinary dispatch; Pydantic Evals is loaded only for explicit benchmark execution.

Drawing cases evaluate supplied revision notices/dimension schedules, not raster drawing interpretation. Market cases evaluate supplied dated synthetic observations, not current market research. Existing separate browser, visual source and provider capability acceptance remain necessary.

Observed during implementation: dataset validation and all 24 deterministic probes ran locally with no AI requests. The approved-job driver was tested using a clearly injected synthetic model through real import, approval, tool and artifact services. Live 72-attempt engine/model runs remain unperformed until an explicit account, model and positive budget are supplied.
